## 0. 使用须知（先读，本手册的效力边界）

> ### ⚠ 本手册所有性能数字均为「建议基线」
>
> **本手册出现的每一个性能数字（30fps / L0 ≤30 / L1 ≤60–80 / L2 ≤120 / 平板折叠可 ≤150（本轮不适用，见 §4.2 裁定） / 300–400 MB / 80–120 MB / 150 MB / 150–200 MB / 美术占比 ≤60% / p95 ≤ 16ms / < 100ms）都是「建议基线」，不是承诺值、不是已定指标，也从未被本机测量过。**
>
> 这些数字的唯一来源是 `design/art/art-bible.md` **§9.4** 与 `docs/architecture/architecture.md` **§10.1**，其性质由架构 §10.1 明确为「仅作测量起点」。

1. **本手册不冻结任何数字。** 冻结 = 把某条建议基线改判为硬指标，该动作**只能由主理人确认**（`production/epics/epic-breakdown.md` §7.2 **P-7**；`tests/quality-closure.md` §2 **O-5**）。本手册连「候选值」都不产出 —— 候选值需要实测，而实测尚未发生。
2. **本手册不是测量结果。** 全篇为「将来怎么测」的步骤说明；任何读者不得据此认为性能已被验证、已被达标、已被校准。
3. **实测值超出建议基线 ≠ FAIL。** 依据 `tests/smoke-checklist.md` **§0.5**：涉及 30fps / DrawCall / 内存 / 首包 / <100ms / 结算 p95 ≤16ms 的项目，**只记录实测值与达标率 % 并与建议基线比对，不得因数值超出建议基线而判 FAIL**。超基线走「降级 → 复测 → 上报」分支（§6），不是质量门失败。
4. **本手册不得被当作验收证据。** 证据是执行后产生的原始记录（§5 表体已填 + 录屏 / Profiler 导出 / 日志），路径规范见 `tests/test-strategy.md` §7.1。本手册本身只是**执行依据**。
5. **测量条件必须可复现，否则数据不可比。** 三件套版本（Cocos 小版本 / HarmonyOS SDK+API / DevEco 版本）必须先钉定（§1.1）；机型、系统版本、亮度、电量、温度状态必须逐轮快照（§5.1）；基准场景必须存档化并每次核对加载后状态（§2.3）。
6. **不得为达标而触碰可访问性与 <100ms 即时反馈。** 见 §9（G6 否决项）。
7. **术语**：本文的「轮」（R1/R2/R3）指**三轮独立测量**，每轮之间必须杀进程冷启 + 静置降温（§4.0）；「次」指一轮内的单次采样。

> 每张记录表（§5 全部表体、`raw-measurement-sheet.md` 全部表体）必须原样带一句表头声明：
> **「建议基线，非承诺值，未冻结。本表实测列在真机执行前一律留空。」**

### 2.2 存档化与可重复加载

- **做法**：把该状态经 `src/save/` 的 `SaveService` 落成一份存档（`SaveSlot`），并在测量设备上以**同一份存档 + 同一 `configHash`** 反复加载。
- **不可变的部分**：`schemaVersion` / `configHash` / `engineVersion` / `seed` 必须每次加载后与存档 header 一致；`configHash` 由 `computeConfigHash`（`src/core/config.ts`）从配置表派生，**配置一改 hash 就变，本批测量即失效**（架构 §4.1 版本组）。
- **一致性机制**：`SaveService.load()` 会对 header 与槽内容做 `checksum` 双处比对（`computeSaveChecksum`，基于 `canonicalize` 键排序 + TypedArray 展开）。checksum 不符 → 拒绝载入。**checksum 定位是防误改 / 防写坏，不是防篡改、不是反作弊**（`src/save/types.ts` 头注），不要在本手册语境里把它当安全能力。
- **介质口径**：本仓库存档层当前为**内存模拟介质**，真机持久化未验证（`src/save/index.ts` 头注；**EX-03 顺延、准出阻塞**）。因此「基准场景一键加载」在真机侧**依赖 K-4 的沙箱 / KV 接口核对完成后才能落地**——这一条是本手册的**未解前置**，不是已知可用的能力。

## 4. 逐项采集步骤（对应 `architecture.md` §10.3 **Step 3**）

### 4.0 通用执行规则（每一项都适用）

1. **每项 3 轮**（R1 / R2 / R3），每轮独立：**杀进程 → 静置降温至当轮首测前水平 → 快照环境（§5.1）→ 加载基准城 → 按 §2.3 自检 → 再开始采样**。
2. **每轮内**按该项规定的采样次数采；记录**单次原始值**，不要只记汇总。中位数由 3 轮结果取（每轮先在本轮内取中位数，再对 3 个中位数取中位数），并在备注写出是否出现离群（如某轮显著偏高，检查是否温度 / 后台干扰）。
3. **不删数据**：离群轮次不得直接丢弃；标 `outlier` 并在备注写原因。若确因环境失控（如充电、后台下载）而废轮，须在 §5.1 记录并说明，且补足 3 个有效轮。
4. **一次只测一项**：同一轮内不要连续切 5 个测量项；项与项之间至少静置 10s（避免上一项遗留的 GC / 纹理上传影响下一项）。
5. **采样必须能溯源**：每项至少留 1 份原始产物（Profiler 导出 / 录屏 / 日志片段），路径记入记录的 `evidence` 字段。
6. **达标率类指标记百分比，不记单次**（§4.7 明确）。

### 4.8 纹理格式探测（ASTC / ETC2 实际生效）

| 字段 | 内容 |
| --- | --- |
| **指标定义** | 两件事分开记：① **能力探测结果**（引擎 / 设备报告支持什么，即 `probeTextureFormat(caps)` 的输出：ASTC → ETC2 → RGB565 → NONE 降级链走到了哪一步）；② **实际生效格式**（GPU 里纹理真实使用的压缩格式）。两者可能不一致（探测说支持 ASTC，导出产物却仍是未压缩）——这个不一致恰恰是本项要抓的东西。 |

### 4.9 合批是否生效

| 字段 | 内容 |
| --- | --- |
| **指标定义** | 判断「同图集 + 同材质 + 相邻层级」的对象是否真被打成一个批次。判据不是「DrawCall 小」，而是**DrawCall 数与图集数 / 材质数的关系**：理想情况 DrawCall 数量级 ≈ 图集数 × 层级分组数；若同图集内 N 个对象产生 N 个 DrawCall，说明合批未生效。 |
| **采集工具** | Profiler 渲染统计（DrawCall / Batches）+ 运行时对象统计（同图集对象数、材质数）；抓帧工具看单帧批次顺序（可选，用于确认是否跨图集交替绘制）。 |
| **操作步骤** | 1) 在 `SC-A`（L1）下统计：当前同屏图集数、材质数、DrawCall；2) **对照试验**：临时只显示单一分区（如仅居住区）→ 记录 DrawCall；再显示三类分区 → 记录 DrawCall；若 DrawCall 增量 ≈ 分区数（而非对象数），说明按图集合批生效；3) 记录「同图集对象数 → DrawCall 数」的比值（例：某图集 200 个对象产生 2 个 DrawCall = 生效；产生 200 个 = 失效）；4) 观察 pan 过程中是否出现**批次抖动**（同屏内容不变但 DrawCall 跳变 → 跨图集交替绘制，对应 art-bible §9.3 / §2.3 的禁止项）；5) R2 / R3 重复。 |
| **记录字段名** | `batch_effective`（`yes` / `partial` / `no`） / `batch_atlas_n` / `batch_material_n` / `batch_dc_per_atlas` / `batch_obj_to_dc_ratio` / `batch_jitter_observed` / `batch_evidence` |
| **判定口径** | **无建议基线数值**（本项是机制验证）。口径：`batch_effective = no` / `partial` 或观察到 `batch_jitter_observed = yes` → 记问题并上报，因为这会同时抬高 §4.2 DrawCall 与 §4.3 纹理内存（重复上传），并可能触发架构 §6.3 的降级（「进一步合并图集 + 减少层级」，**不引入逐对象材质**）。**合批失效不得用「减少内容」解决**，只能改图集与层级组织。 |

```

  │     ├─ 步骤 3：复测达标 → 记录「降级前 / 降级后」两组值（两组都保留，不许只报降级后）
```

**分支纪律（硬约束）**：
1. **降级顺序不得跳级、不得并行乱序**（架构 §10.4）。第 5 级「低档关闭全部 VFX」是最后一档，不是第一反应。
2. **降级不得触碰可访问性与 <100ms 即时反馈**（§9；G6 否决项）。任何「为了帧时间关掉图案层」的提议**直接否决，不得进入上报**。
3. **不得为达标而改基准场景**（换小城、减议题、删拥堵链路）—— 那会让数据与后续批次不可比，属数据造假。
4. **实测超出建议基线不得据此判 FAIL**（`tests/smoke-checklist.md` §0.5 原话口径）。S-12 的验收 4 是「**覆盖**这些采集项」＋「产出校准报告」，不是「实测值必须达标」。超基线是**正常的校准发现**，处置是降级 / 上报。
5. **不得把「降级后达标」写成「性能达标」**：降级后达标只说明「该档位下可用」，必须同时写明降级项与该档位适用机型。

### 9.4 热区基线口径（2026-11-07 由 44dp 上调至 48dp）

> 依据来源：华为《通用应用 UX 体验标准》**2.1.3.3 点击热区**（标准等级：必须；适用手机 / 折叠屏 / 平板）。条文原文**由主理人核实**后转达（2026-11-07）；本手册未独立复核官方原文。

1. **48dp 取的是官方「推荐」值，不是唯一数值**：官方要求可点击热区 ≥40vp×40vp（必须下限），推荐 ≥48vp×48vp；**本项目现行值取推荐值 48dp**（`MIN_TAP_TARGET_DP` 上调至 48）。原值 44dp 只满足「必须」下限、未达「推荐」档，故于 2026-11-07 上调——**44dp 是历史值，不再作为现行基线**。
2. **单位口径**：官方条文用 `vp`，本项目代码用 `dp`，二者概念等价（密度无关像素）；**对外表述时单位名须与官方口径一致**——引官方条文写 `vp`，写本项目实现写 `dp`，不要混用成「48vp 的代码常量」这类表述。
3. **间距 ≥8dp 不是官方条文**：官方只有「8vp 网格系统」（布局对齐基线）；相邻热区间距 ≥8dp 是**项目设计决策**（ux-spec §7 E5），**不得**对外表述为「鸿蒙规定相邻间距 ≥8vp」。
