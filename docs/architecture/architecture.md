## 0. 文档定位、范围与不可变前提

### 0.1 用户已拍板、架构必须支撑且不得更改的前提

1. **平台**：HarmonyOS 7（开发者预览 / 测试阶段，HarmonyOS SDK 26 / API 26）；手机竖屏优先，兼容平板与折叠屏。
2. **引擎链路**：Cocos Creator 3.x 官方适配 HarmonyOS NEXT → 导出 HarmonyOS 工程 → DevEco Studio 打包 HAP；2D 管线 + 2:1 dimetric 等距（128×64 格）。
3. **形态**：固定 2.5D 等距、低频 tick、网格地图、密集 UI。
4. **核心设计决策（OD 全为 A）**：
   - **OD-1 A**：市民满意度唯一计分板，无硬终局，未达标**可回退重试**。
   - **OD-2 A**：主动推进制，默认暂停，玩家点「结束本日」结算一次 tick，思考时间无限；×1×2×4 自动播放为 Should 期可选，**不进首版 Must**。
   - **OD-3 A**：聚合数据 + 少量「市民之声」文本，**不做具象个体市民模拟**。
   - **OD-4 A**：固定有限网格（概念建议 24×24~32×32），按里程碑解锁新区。
5. **平台特性纪律**：H1 秒启卡片 / H2 折叠屏双栏 / H3 跨设备流转一律**不进 Must**；H4 分布式多机同局为 **Won't**；任何平台特性须标注「**须真机验证后方可排期**」。

> 本文不复议上述五条，只在其边界内给技术结论。任何突破须回到用户 / 主理人拍板。

### 0.3 术语与缩写

| 术语 | 定义 |
| --- | --- |
| NAPI / Node-API | HarmonyOS 提供的 JS/ArkTS ↔ C/C++ 跨语言调用接口（类 Node.js N-API），Cocos 引擎经此与 ArkTS 应用层桥接 |
| XComponent | HarmonyOS 自定义绘制组件，提供原生 Surface 供 OpenGL ES / Vulkan 渲染，Cocos 渲染面挂在其上 |
| HAP | HarmonyOS Ability Package，DevEco Studio 产出的应用包 |
| Command（命令） | 玩家一次决策的结构化意图（划 / 拨 / 连 / 推 / 撤销），是模拟层唯一输入 |
| TickSnapshot（快照） | 一次 tick 结算后**自包含**的权威状态 + 元数据，可独立恢复 / 回放 |
| Δ_t（差分包） | S_t → S_{t+1} 的逐指标差分（旧值 / 新值 / 变化量 / 方向） |
| 归因链 AttributionChain | 结算 pipeline 中「顺带记录」的因果记录：某指标变化 → 指向具体通勤线 / 覆盖不足片区 / 预算项 |
| Keyframe / Delta | 全量锚点快照 / 增量差分，混合保留策略（§4.3） |
| LayoutProfile | 平台适配层输出的「形态 → 布局」配置，UI 树消费它重排，不碰系统 API |
| VM（视图模型） | UI 层持有的只读投影 + 本地乐观叠加，**不是权威状态** |
| dp / sp | 与密度无关的逻辑长度 / 字号单位；安全区、热区、文本缩放统一走此注入 |

## 1. 技术选型与鸿蒙适配路线

### 1.1 选型结论（不复议，只落地）

| 层 | 选型 | 依据 |
| --- | --- | --- |
| 游戏引擎 | Cocos Creator 3.x（官方 HarmonyOS NEXT 适配分支） | 用户已拍板；2D 管线对等距 tile、图集合批、UI 密集场景最经济（美术圣经 §2.1 / §9.3） |
| 游戏逻辑语言 | TypeScript，运行于 Cocos 脚本虚拟机 | 与导出链路一致；模拟层写成无平台依赖的纯 TS，可单测 |
| 渲染面 | 2D 管线 + XComponent(Surface) → GLES | 2:1 dimetric 128×64 格，正交网格像素对齐最干净 |
| 平台能力 | ArkTS 应用层（UIAbility / XComponent / 系统 API）经 NAPI 桥 | 安全区、折叠态、文件持久化、生命周期、无障碍、卡片 / 流转预留 |
| 打包 | DevEco Studio → 签名 → HAP | 用户已拍板 |

### 1.2 工程链路（Cocos → HarmonyOS NEXT 导出 → DevEco Studio）

```
[Cocos Creator 3.x 工程]
  游戏逻辑 TS / 场景 / 图集 / 配置表（本仓库 src 与 assets，本轮不建）
        │  构建目标 = HarmonyOS NEXT
        ▼
[Cocos 导出的 HarmonyOS 工程骨架]
  ├─ ArkTS 应用层：UIAbility、XComponent、生命周期回调、权限声明
  ├─ NAPI 桥接层：引擎 C++ ↔ ArkTS 的注册与事件转发
  ├─ Cocos C++ 引擎库（预编译）+ 脚本虚拟机
  └─ resources：游戏资源（图集 / 配置 / 文案）
        │  用 DevEco Studio 打开
        ▼
[DevEco Studio]
  编译 ArkTS / 链接 native so / 资源打包 / 签名
        ▼
[HAP] → 真机（手机竖屏 / 折叠展开 / 平板）→ Profiling（§10）
```

**三条工程纪律（写进控制清单）**：
1. **单一真源**：游戏逻辑、图集、配置表只在 Cocos 工程侧维护；HarmonyOS 工程骨架视为「构建产物 + 平台胶水」，胶水代码量必须最小化，禁止在 ArkTS 层写游戏规则。
2. **版本锁定**：Cocos 小版本、HarmonyOS SDK / API、DevEco Studio 版本三者写入构建锁文件并纳入真机回归；任一升级须重跑 §10 校准。**具体小版本为知识缺口（§1.4）**。
3. **可复现构建**：导出 + 打包脚本化（不在本轮实现），保证任一历史快照的引擎版本可追溯（存档自包含要求，§5.1）。

### 1.3 Node-API / XComponent 边界（关键隔离面）

```
┌───────────────────────────────────────────────────────────────┐
│ ArkTS 应用层（HarmonyOS SDK 能力所在）                            │
│  UIAbility 生命周期 · XComponent(Surface) · window/安全区/折叠态  │
│  文件沙箱 · 无障碍 · 字体/文本缩放 · 卡片/分布式（H1/H3 预留）     │
└───────────────┬───────────────────────────────▲───────────────┘
                │ NAPI（能力注册 / 事件转发）      │ NAPI 回调
                ▼                                │
┌───────────────────────────────────────────────────────────────┐
│ 平台适配层 PlatformAdapter（引擎脚本侧，唯一碰平台的地方）        │
│  ILifecycle · IWindowInsetProvider · IFoldStateProvider          │
│  ISaveStorage · IAccessibilityBridge · IFeatureFlags             │
│  输出：LayoutProfile / 安全区 insets / 系统缩放因子 / 形态枚举    │
└───────────────┬───────────────────────────────────────────────┘
                │ 稳定抽象接口（业务层只见接口、不见 HarmonyOS API）
                ▼
┌───────────────────────────────────────────────────────────────┐
│ 业务层：数据 / 模拟 / 渲染 / UI（纯 TS，零 HarmonyOS SDK 依赖）    │
└───────────────┬───────────────────────────────────────────────┘
                │ 渲染指令
                ▼
        [GLES / XComponent Surface] → 屏幕
```

**边界原则（架构铁律）**：
- 业务层（含模拟核心）**不直接调用任何 HarmonyOS SDK**；一切系统能力经 `PlatformAdapter` 的稳定接口注入。API 26 预览版接口一旦变更，只改适配层，不动游戏规则与快照格式。
- **触控 / 生命周期事件流**：ArkTS 收到触控、`onForeground/onBackground`、surface 创建销毁、折叠态变化 → NAPI 转发 → 适配层转成引擎内事件 → 业务层消费。业务层不感知事件来自哪个系统回调。
- **渲染归属**：Cocos 用 XComponent 的 Surface 建 EGL 上下文；UI 与世界都在 Cocos 场景树内绘制，**不用原生 ArkUI 组件拼游戏 UI**（避免两套 UI 状态、两套安全区、两套动效策略）。ArkUI 只承载极薄的宿主容器与（H1 若做）桌面卡片。

### 1.4 知识缺口与「须真机验证」清单（知识诚实）

> 以下为**超出可确信范围**的部分，本文不臆造 API / 行为，统一登记为知识缺口。**G11 已回执（T-107，2026-11-05）：不补 `docs/engine-reference/` 引擎参考文档**——HarmonyOS 7 / API 26 仍处开发者预览，Cocos 鸿蒙导出的确切小版本、API 26 接口名、ASTC/ETC2 实际支持、HAP 权限与 GPU 水位均未经真机验证，此时写参考文档会把猜测固化成「已确认事实」，反而误导实现。K-1~K-5 **保留为开放缺口**，在 **S-01 空场景真机验证后逐条回填 `control-manifest.md`**（回填时机、责任侧与回填位置见该文件 §5；本文件 §13 G11 同步登记）。

## 2. 分层架构与依赖方向

### 2.1 五层总览

```
        ┌──────────────────────────────────────────────┐
        │ UI 层  HUD / 建造 Tab / 议题列表 / 诊断面板     │  发 Command、订阅事件、持有 VM
        └───────────────┬──────────────────────▲───────┘
                        │ Command              │ 事件 / 差分 / 快照投影(VM)
        ┌───────────────▼──────────────────────┴───────┐
        │ 模拟层 Simulation（核心域 · 纯函数 · 确定性）  │  tick 结算 pipeline、命令应用、归因记录
        └───────────────┬──────────────────────▲───────┘
                        │ 读 / 写                │ 只读视图
        ┌───────────────▼──────────────────────┴───────┐
        │ 数据层 Data  网格状态 / 配置表 / 快照 / 存档   │  纯数据 + schema，零引擎依赖
        └───────────────▲──────────────────────▲───────┘
                        │ 只读                │ 只读
        ┌───────────────┴──────┐   ┌──────────┴──────────────┐
        │ 渲染层 Rendering      │   │ 平台适配层 PlatformAdapter│
        │ 等距 tile / LOD / 图集│   │ NAPI / 生命周期 / 安全区  │
        └──────────────────────┘   └──────────────────────────┘
```

依赖方向（**单向，禁止反向**）：`UI → 模拟 → 数据 ← 渲染`；`PlatformAdapter` 被所有层通过接口依赖，但**不反向依赖任何业务层**；渲染层与 UI 层只「读」数据 / 快照投影，**绝不回写权威状态**。

### 2.2 单向依赖铁律（编码标准 · 路径作用域）

| 层 | 允许 | 禁止 |
| --- | --- | --- |
| 平台适配 | 调 HarmonyOS SDK / NAPI；输出抽象接口与 LayoutProfile | import 任何游戏规则、持有城市状态、写快照 |
| 数据 | 定义 schema、配置表加载、序列化 / 校验和 | 调引擎渲染、调系统 API、含业务规则分支 |
| **模拟** | 纯 TS 计算；输入 = 快照 + 命令 + 配置；输出 = 新快照 + 差分 + 归因 | **零热路径分配**（避免每 tick GC）、依赖墙上时钟、不可控随机、遍历顺序不确定、调渲染 / 平台 API |
| 渲染 | 读只读视图、按 LOD 绘制、播世界状态动效 | 写状态、直接改数值、绕过语义令牌取色 |
| UI | 发 Command、订阅事件、渲染 VM、本地乐观反馈 | **持有权威游戏状态**、直接改网格 / 预算、把反馈绑到 tick（§7） |

> 模拟层「可调试」：每个结算阶段输出中间量（§3.2），任一 tick 可离线重放；AI / 规则若后续引入，只能以「可注入策略」形式挂到 pipeline 阶段，不得散落各处。

### 2.4 关键横切机制（一句话定义，避免各处重复实现）

- **Command**：玩家意图的唯一载体，带 `tickId` / `seq` / 幂等键；UI 只产命令，不产状态。
- **Event**：tick 提交后广播（`TickCommitted`、`IssueAppeared`、`BudgetRejected`、`FoldModeChanged`…），带 `schemaVersion`。
- **Snapshot / Δ / 归因链**：模拟层的三件套产物，UI / 诊断 / 存档 / 回退共用**同一份**，禁止各模块自行重算。
- **SemanticToken**：分区 / 状态 → 视觉编码的唯一映射（可访问性刚需，§9.1）。
- **MotionPolicy**：全局「减少动态效果」开关，所有动效组件查询它；即时反馈在该开关下**改为瞬时静态反馈而非取消**（§7.4）。
- **LayoutProfile**：形态 → 布局的单一输出，含安全区 insets（§8）。

## 3. 模拟循环与 tick 结算顺序（OD-2 A 落地）

### 3.1 双循环模型：**渲染帧循环** 与 **tick 结算** 彻底解耦

```
渲染帧循环（每帧 ~33ms @30fps 基线，永不推进模拟）
  ├─ 采集触控 → 生成 Command 投 pending queue
  ├─ 即时 UI 反馈（<100ms，§7）           ← 与 tick 无关
  ├─ 世界状态动效插值（可关闭）
  └─ 渲染（等距视图 / LOD / HUD）

tick 结算（事件驱动、一次性同步事务；仅 V6「结束本日」触发）
  └─ 冻结输入 → P0~P8 结算 → 提交 S_{t+1} + Δ_t + 归因链 → 落盘 → 广播
```

**OD-2 A 的三条直接结论**（概念 9.2 第 1 项的技术落点）：
1. **没有「每帧跑模拟」这回事**。模拟不是循环，是一次**离散原子事务**；tick 之间城市状态冻结、思考时间无限。渲染帧率波动不影响模拟结果。
2. **不需要后台运行 / 保活 / 精确闹钟 / 离线结算 / 时间同步**（对比 OD-2 C）。切后台只需冻结并保存当前快照（§5.2）。
3. **暂停中的操作不丢失也不裸改状态**：进入 `CommandQueue` 排队，UI 同步给乐观反馈；点「结束本日」时一次性应用（概念 OD-2 边缘情况第 1 条）。

### 3.2 tick 结算 pipeline（阶段顺序即归因顺序）

> 每一阶段都把中间量写进 `AttributionRecorder`——**归因在结算时记录，不在诊断时重算**（概念 9.2 第 5 项核心）。

| 阶段 | 名称 | 输入 | 输出 / 记录的诊断量 | 对应规则 |
| --- | --- | --- | --- | --- |
| **P0** | 冻结输入 | pending queue | 锁队列、生成 `tickId`、去重幂等；结算中重复点按被 InputGate 拒（OD-2 边缘第 2 条） | R5 |
| **P1** | 应用命令 | S_t 工作副本 W + 命令 | 分区 / 预算 / 道路变更；合法性校验（不可透支、地块状态、连通预检）；非法 → `BudgetRejected` 记录供 UI 回滚乐观视图 | R1 R2 R3 R4 |
| **P2** | 通勤图求解 | W 的路网 + 分区块 | 链路流量、通行时间、容量利用率；记录「哪条线变慢」 | R4 / P3 / D1 D2 |
| **P3** | 服务覆盖 | P2 的有效抵达 | 各分区覆盖因子；记录「哪片覆盖不足」——**必须走通勤网络，禁止纯半径叠 buff**（P3 否决项） | R4 R6 |
| **P4** | 满意度合成 | 4 因子（通勤 / 覆盖 / 环境 / 财政）；**财政投入因子 `f_f` 取上一 tick / 上一周期已拨付值，不读本 tick 经济结果** | 全局满意度 `S_t` + 逐因子值 + 因子贡献分解；记录每因子贡献差分 | R6 / P1 |
| **P5** | 经济按 tick 记账（**非周期结算**） | 建设支出登记、维护费累计 | 累计账目；软着陆（告警而非瞬死，R5） | R3 |
| **P6** | 议题与市民之声 | 显著变化 + 归因链 | 议题生成 / 消退、聚合文本引用 id（**不做个体模拟**，OD-3 A） | R8 / D4 |
| **P7** | 周期判定与预算结算（**仅周期末 tick**） | 累计 tick 数 + **`S_{t-1}`** + 已拨付预算 | 用 **`S_{t-1}`** 结算 `I_t / C_b / C_m / B_t`，**`f_f,t` 取上一周期已拨付值**；目标判定为满意度单轴；**无「失败终局」**，未达标只标记「可回退重试」（OD-1 A） | R7 |
| **P8** | 提交 | 上述全部 | `S_{t+1}` + `Δ_t` + 归因链 + keyframe/delta 入库 + SaveService 落盘 + 广播 `TickCommitted`；快照含 **`t-1` / `t` 双帧**，保证 `S_{t-1}` 在周期结算时可读且不被覆盖 | R5 R8 |

**顺序不可交换的理由**：P2→P3→P4 是因果链（位置决定通勤，通勤决定覆盖，覆盖与其余因子合成满意度），倒序会破坏 V2 诊断的可追溯性（AC2）。**P4 不读 P7 的本周期收入**（D6 解环见下）。

### 3.2.1 与 `systems-index.md` §4.3 统一步序对齐，及 D6 单 tick 滞后解环（回应待架构确认项 A-1 / A-5）

> `design/gdd/systems-index.md` v1.0 已给出**统一 tick 结算顺序**（其 §4.3 ①~⑧）并裁定 D6 用「单 tick 滞后」解环（其 §3.3）。架构侧**对齐设计侧裁定，不另立顺序**；下表是本文 P0~P8 与设计侧步序的映射，二者描述同一条结算链。

| 设计侧 §4.3 步序 | 本文阶段 | 对齐说明 |
| --- | --- | --- |
| 冻结输入（读 `t-1` 末快照 + 暂停态已提交编辑） | P0 + P1 | 默认暂停、批量提交、InputGate 幂等（**A-1**） |
| ① 02 输出地块状态 / OD 需求 | P1 → P2 输入 | 分区块 OD 需求由数据层提供 |
| ② 03 求解通勤图，输出 `T_c` 与拥堵系数 | P2 | 合并分区块求解、不可达显式处理、除零保护（**A-3 / A-4**） |
| ③ 01 计算 4 因子（`f_f` 取上一周期已拨付值） | P4 前半 | **不读本 tick 经济结果** |
| ④ 01 合成 `S_t`、计算 `ΔS` 与因子贡献分解 | P4 后半 | 产出 `Δ_t` 与归因链 |
| ⑤ 01 写状态快照（`t-1`/`t` 双帧 + 归因链） | P8 | 架构把提交放在**末尾**，使快照同时覆盖 P6 议题与 P7 预算告警；`t-1` 帧常驻保证 `S_{t-1}` 可读（**A-2 / A-5**） |
| ⑥ 05 生成 / 更新 / 消退议题 | P6 | 议题数 2~4（3±1 硬上限） |
| ⑦ 周期末：04 用 `S_{t-1}` 结算 `I_t/C_b/C_m/B_t` 并做目标判定与解锁 | P7 | **仅周期末 tick 执行**；与 P4 不形成同 tick 循环 |
| ⑧ UX 刷新（≤3 指标 + 议题列表） | P8 广播后 | 双通道（ADR-004）：tick 结果走通道 B，即时反馈走通道 A |

**D6 解环（架构落地，正面回答 A-5）**：
- `S_t` 的计算（P4）**只读** P2/P3 结果与「上一 tick / 上一周期已拨付的 `f_f`」，**不读 P7 的本周期收入 `I_t`**；
- `I_t`（P7）由 **`S_{t-1}`** 计算，`f_f,t` 取上一周期已拨付值；
- 因此 `S_t` 不依赖 `I_t`，闭环被打破；`t-1` 帧由快照双帧策略保证「可读且不被覆盖」；
- 该滞后同时是 D4「滞后暴露」的因果来源，归因链须把「因 `S_{t-1}` 导致的收入变化」记入 P7 诊断量，供 V2 追溯。

### 3.3 确定性、输入闸门与状态冻结

- **确定性**：`S_{t+1} = F(S_t, commands, config)` 为纯函数。禁止墙上时钟、禁止 `Math.random()`（改用**可种子化 PRNG**，种子入快照）、禁止依赖 Map/Set 遍历顺序、禁止浮点累加顺序随平台变化（关键求和用定点 / 受控顺序）。同一 (S_t, 命令, 配置) 重放必须**逐字节一致**。
- **输入闸门**：P0 加锁 → P8 解锁；结算期间的「推 / 划 / 拨 / 连」一律排队或拒绝并给即时反馈，**绝不允许半结算状态被再次触发**（OD-2 边缘第 2 条）。
- **切后台 / 折屏切换**：由 `ILifecycle` 触发「冻结 + 落盘」，不推进 tick、不读墙上时钟；回来时从最近快照恢复，形态变化只重排 UI（§8.2），**不重置模拟状态**（OD-2 边缘第 3 条）。

## 4. 状态快照、差分与回退（OD-1 A / V2 诊断 / 概念 9.2 第 5 项）

### 4.1 TickSnapshot 结构（**自包含**是硬要求）

| 字段组 | 内容 | 为何必须 |
| --- | --- | --- |
| 标识 | `tickId`（单调递增）、`cycleId`、`cycleTickIndex` | 回退定位、H3 若做时的版本基准 |
| 版本 | `schemaVersion`、`configHash`（公式 / 权重 / 建筑表版本）、`engineVersion`、PRNG `seed` | 旧存档在新版本下能判定「可否续算」；配置一改不能静默算出不同结果 |
| 权威状态 | 网格（分区 / 密度 / 道路 / 建筑引用）、预算、4 因子明细、全局指标、议题列表、市民之声引用 id | 恢复即完整城市 |
| 诊断 | `Δ_t`（逐指标旧 / 新 / 变化量 / 方向）、`AttributionChain_t`（变化 → 原因条目） | V2 诊断**直接查**，不重算模拟（§4.2） |
| 输入溯源 | 本 tick 应用的命令列表（含幂等键） | 回放 / 审计 / 撤销 |

> 「自包含」= 仅凭这一份快照（+ 对应版本的配置表）即可恢复并继续结算，不依赖「之前发生过什么」的隐式上下文。这是回退、回放、未来 H3 迁移的共同前提。

### 4.2 差分包 Δ_t 与归因链

- **Δ_t**：每个可读指标一条 `{ key, old, new, delta, direction, magnitude }`。UI 的「数值滚动 / 箭头 / 正负色」直接消费它，不自行相减（避免两处算法不一致）。
- **归因链**：每个显著变化 ≥1 条 `{ metricKey → causeType(通勤线 / 覆盖片区 / 预算项 / 环境源) → refId → contribution }`。由 P2~P5 顺带写入。
- **为什么不「查询时重算」**：① 重算要重跑 P2 流量求解，玩家点开诊断面板会卡顿；② 配置版本一变，用新公式重算旧 tick 会得到与当时不一致的结论，AC2「可追溯」失真；③ 诊断面板必须 <100ms 级响应（美术圣经 §6.6 的分层精神）。**结论：结算时记录、查询时只读取。**

### 4.3 保留策略：Keyframe + Delta（关键帧 + 差分），覆盖 D4 滞后暴露

概念 D4 明确「负面后果在 2~3 个周期后才浮现」，诊断与回退必须能**跨 ≥3 个周期**回溯；但逐 tick 全量快照会撑大内存。采用混合策略：

| 类型 | 内容 | 保留范围 | 估算体积 |
| --- | --- | --- | --- |
| **Keyframe（全量锚点）** | 完整权威状态 + 指标 + 议题 | 每个市政周期**首 / 末** tick，以及每次回退目标点 | 约 100–300 KB / 份（估算依据见下） |
| **Delta（增量）** | Δ_t + 归因链 + 命令列表（不含逐格全量） | 周期内每个 tick；热窗口保留最近 **K = 一个周期的 tick 数**（建议 24，依 GDD 钉定）常驻内存 | 约 5–20 KB / tick |
| **冷归档** | 最近 ≥3 个周期的 keyframe + delta 序列 | 落盘存档，按需读入 | 3 周期 ×(2 keyframe + 24 delta) ≈ 3 ×(0.6 MB + 0.48 MB) ≈ **3.2 MB** 量级 |

**体积估算依据**：每格状态（分区 1B + 密度 1B + 道路 1B + 建筑引用 2B + 覆盖 / 流量浮点 ~16B + 预留）约 **24–64 B/格**；32×32=1024 格 → 权威状态 **24–64 KB**；加 4 因子明细、指标、议题、归因条目（每 tick 数十条 × 数十字节）→ 单份全量快照 **100–300 KB** 量级。差额分只有指标级数据，故小一个量级。→ **常驻内存（热窗口 24 delta + 2 keyframe）≈ 1 MB 以内，冷归档 ≈ 几 MB，完全可控**（美术圣经 §9.4 应用总内存建议 300–400 MB，模拟数据占比极低）。

**回退重试如何复用快照（OD-1 A，概念 9.2 第 5 项后半）**：
- 因 `F` 是确定性纯函数 + 命令溯源，**回退不需要「反向运算」**，只需「把权威状态指针重置到某个 keyframe，丢弃其后的 delta，从该点重新决策」。
- 两种粒度：
  - **tick 级撤销**（撤销本日）→ 重置到 `S_t`（上一 tick 的 delta 链末端 / 最近 keyframe + 重放前序 delta）。
  - **周期级重试**（未达标回退）→ 重置到**周期起始 keyframe** 并清空该周期所有 delta；这正是 P7 只「标记可回退」而不「判负」的落点。
- 快照自包含 + `configHash` 保证「回退后继续算」与「当时算」一致；`tickId` 单调递增避免回退后 id 冲突（回退后新分支沿用新 id，旧分支 delta 归档保留供复盘）。

## 5. 存档与数据一致性（ADR-003 摘要）

### 5.1 存档内容

```
SaveSlot = {
  header:  { schemaVersion, configHash, engineVersion, saveTime(仅展示用) },
  current: 最近一份 Keyframe + 其后的 Delta 链（或直接最近全量快照）,
  ledger:  最近 ≥3 周期冷归档（诊断 / 回退用）,
  prngSeed,
  checksum,
}
```

MVP = **本地单存档 + 断点续玩**（概念 §5.1 存档 Must）；多存档位、云同步均为 Should/Could，不在首版。

### 5.2 OD-2 A 的架构红利（概念 9.2 第 1 项结论之一）

| 因为 OD-2 A | 所以**不需要** |
| --- | --- |
| 默认暂停、手动 tick、无现实时间推进 | 后台保活权限、精确闹钟、离线结算、墙上时钟基准、设备间时间同步 |
| tick 稀疏（玩家主动触发） | 每次结算后落盘的开销完全可接受，无需增量 / 差量写优化 |
| 状态冻结 | 切后台只需「冻结 + 存一次」，回来从快照恢复，无「补算漏掉的 tick」问题 |

> 对比 OD-2 C（现实时间制）：需后台权限 + 离线补算 + 时间基准一致性 + 防篡改时钟，架构复杂度显著上升，且与 Pastime 美学冲突。**拍板 A 是架构最轻的路径，本文不复议。**

### 5.3 落盘、完整性与迁移

- **时机**：P8 每次提交后原子写；`ILifecycle.onBackground` 强制再存一次；关键操作（回退、解锁新区）后存。
- **原子写**：写临时文件 → fsync → rename；或 **A/B 双槽**交替写，任一时刻至少一个完好槽。加载失败 / checksum 不符 → 回退上一完好槽并提示，绝不加载半损坏存档。
- **完整性**：`schemaVersion` + `configHash` + `checksum`。版本不匹配 → 走显式迁移器（无迁移器则拒绝载入并保留旧槽），**禁止静默用新公式续算旧档**（§4.1）。
- **轻量安全定位**：单机无对抗、无 PvP（概念 §2.3 排除项）。此处 checksum 用于**防误改 / 防写坏**，不是反作弊；不做强加密 / 防篡改（标注清楚，避免被误读为安全承诺）。
- **存储抽象**：一律经 `ISaveStorage`；优先应用沙箱文件 / 系统 KV 偏好（**具体接口待真机核对 K-4**），业务层不碰路径与权限。

### 5.4 H3 预留但不实现

`ISaveStorage` 接口签名预留「远端读写 + 版本向量」的能力位、`tickId` 单调递增、`configHash` 齐备——使未来若开启 H3，不必重构数据层。**但本轮不实现任何同步逻辑**，理由见 §11.4（概念 9.2 第 4 项）。

## 6. 资源加载与图集分包

### 6.1 分包策略（对齐美术圣经 §9.3，架构负责加载机制）

| 包 | 内容 | 加载 | 卸载 |
| --- | --- | --- | --- |
| `UI` + `UI-图案编码` + 字体令牌 | 图标 / 9-slice 面板 / 状态条 / 分区图案层 | **常驻**（首屏即需，可访问性刚需，不参与降级） | 不卸载 |
| `地形地块` / `道路` / 网格线 | 基础 tile | 常驻（首屏） | 不卸载 |
| `建筑-{分区}` × N | 各分区三档密度资产 | **按激活分区集按需加载** | 分区未解锁可懒加载；切 LOD 不卸载（三档同图集） |
| `车辆+市民` / `VFX` / `昼夜窗光` / `天气` | 表现层 | 按 LOD / 性能档位加载 | L0 或低性能档可跳过 / 释放 |

**铁律**：LOD 三档资产打入**同一图集**（美术圣经 §2.3），避免切换时跨图集打断合批；UI 图标全部入 UI 图集；**禁用逐对象独立材质 / Shader 变体**（§9.4）。

### 6.2 加载时序与内存水位

```
冷启动 → 载入 UI / 地形 / 道路常驻包 + 配置表 + 存档
       → 从最近快照恢复渲染视图（首屏）
       → 按当前激活分区集异步加载建筑包
       → 按 LayoutProfile / 性能档位决定 VFX / 天气是否加载
       → 运行期：里程碑解锁新区时增量加载对应分区包（OD-4 A）
```
内存水位由「常驻包 + 当前 LOD + 已解锁分区集」决定；低性能档优先不加载天气 / 夜间窗光 / VFX 粒子（美术圣经 §9.4 降级顺序）。

### 6.3 ASTC / ETC2 与合批未验证的降级（K-3，美术圣经 D-1）

- `PlatformAdapter` 提供**纹理格式能力探测**（启动时一次性）：优先 ASTC → 回退 ETC2 → 不透明底可 RGB565；UI 图标 / 文字图集保持不压缩保清晰度。**探测结果写入性能校准记录**，不写死在资源里。
- 合批行为按「同图集 + 同材质 + 相邻 UI 层级」组织（美术圣经 §9.3）；真机若发现导出分支合批失效，降级为「进一步合并图集 + 减少层级」，**不引入逐对象材质**。
- 所有上述结论**须真机验证后方可排期**为硬约束；未验证前 §9.4 数字一律保持「建议基线」。

### 6.4 分区类型数据驱动加载（化解跨专业冲突 X-2）

分区类型做成**可扩展枚举 + 配置表**：MVP 激活集 3 类（居住 / 商业 / 产业，概念 §5.1 Must），其余分区（公共服务 / 办公 / 公园 / 市政，美术圣经 §3.2 的 6 区）作为 Should 预留。图集分包、分类 Tab、图案编码表**全部由配置生成**，不写死数量。这样无论主理人裁定采用 3 区还是 6 区，加载层与 UI 层都不返工。

## 7. UI 与模拟解耦（<100ms 即时反馈 · ADR-004 摘要 · 美术圣经 D-3 / §6.6）

### 7.1 双通道模型

```
通道 A · 即时反馈（同步、帧内，<100ms，不受 tick 约束）
  玩家操作 → UI 本地生成「乐观视图」（落位高亮 / 按压态 / 扣减动画 / Tab 切换 / 选中描边）
           → 同帧或下一帧渲染
           → 同时把操作包装为 Command 投入 pending queue

通道 B · 模拟结果（事件驱动，仅 V6 触发）
  「结束本日」→ TickPipeline 结算 → Δ_t / 归因链 / 事件广播
           → UI 按 Δ 做指标滚动、议题出现/消退；渲染层播世界状态动效（可关闭）
```

> 美术圣经 §6.6 / D-3 的风险原话：「若把 UI 反馈也绑到 tick，玩家会感到『点了没反应』」。**本双通道即对该风险的架构答复**：反馈与结算走两条路，互不阻塞。

### 7.2 乐观视图与 VM（UI 不持有权威状态）

- UI 只持有 **VM = 快照投影（只读）+ 本地乐观叠加（视觉）**。权威值永远以 P8 的 Δ_t 为准。
- 若命令在 P1 被判非法（如预算不足）→ 广播 `BudgetRejected` → UI **撤下乐观视图**并给负向反馈（形状编码 ✕，§9.1）。既保证 <100ms，又不显示错误数值。
- **结构约束**：代码评审检查「UI 层无任何写网格 / 写预算 / 写满意度的路径」（§2.2 / §13 G3）。

### 7.3 帧预算归属与输入闸门协作

- 即时反馈走渲染帧循环；tick 结算是独立事务，二者不互相阻塞。结算耗时须短到玩家无感（建议逻辑结算 p95 ≤ 16ms，§10.1），期间由 InputGate 显示「结算中」态锁输入（§3.3）。
- 倍速 ×1×2×4（Should）若日后开启，本质是「按间隔自动产生 V6 命令」，**不改变本分层**：仍走通道 A 反馈 + 通道 B 结算，只是命令来源从「手动」变「定时器」。首版 Must 不含，feature flag 默认关（跨专业冲突 X-1）。

### 7.4 「减少动态效果」下的即时反馈

`MotionPolicy` 开启时：loop 动效 / 粒子 / 相机缓动停播，昼夜 / 缩放瞬时切换（美术圣经 §8.1 / §9.2）；**即时 UI 反馈不取消，改为瞬时静态反馈**（描边 / 色块 / 数值直变），保证「信息传达」不丢失、仍 <100ms。可访问性优先于表现（§9.3）。

### 8.1 UI 框架所需能力清单（由 LayoutEngine + PlatformAdapter 提供）

### 8.2 形态 → 布局映射与回退状态机

| 形态 | 布局 | 判据 |
| --- | --- | --- |
| `folded`（合盖 / 手机竖屏） | 单栏 §6.2：底部拇指热区、≤3 指标、议题列表 | 默认 / 兜底 |
| `unfolded`（展开，横向铰链） | 上下双栏：上半屏只读画布 + 极简状态条；下半屏全部交互控件，铰链上下各留 ≥24dp | 折叠态接口可用且可信 |
| `tablet`（横屏） | 左画布 ≥70% 宽 + 右侧常驻双列面板，小地图右下 | 视口宽高比 + 折叠态 |
| `multi-window / split` | 按可用宽度退化为单栏或紧凑双栏 | 视口尺寸 |
| **未知 / 接口异常 / 读取失败** | **统一回退 `folded` 单栏** | 保守兜底 |

**回退原则（明确结论）**：**功能不降级，只降信息密度增益**。任何形态下 V1–V9 完整可达（概念 §5.2「手机竖屏可完整通关」）；双栏只是「展开态默认展开一级详情面板」这类增益（美术圣经 §6.3 明说不额外增加资产），回退到单栏只丢增益、不丢功能。形态切换与模拟状态完全无关（解耦红利）。

### 8.3 铰链 / 安全区接口不稳定时的降级方案（美术圣经 D-2 要程基岩给）

K-2 已登记：API 26 预览版折叠 / 避让区接口名与稳定性未知。降级按以下顺序启用，且**全部标注「须真机（含折叠展开态）验证后方可排期」**：

1. **不依赖折叠态 API 做形态判断**：改用「视口宽高比 / 可用宽度阈值」的启发式判定（宽 ≥ 阈值 → 可作双栏，否则单栏），绕开不稳定的 foldStatus 接口。
2. **精确 insets 读不到时保守留白**：采用美术圣经 §6.3 给的降级——「固定上下分栏 + 手动留白 24dp」，四边再加保守内边距；**关键控件 / 选中态 / 关闭按钮一律不放在中央铰链带**。
3. **整体安全容器内缩**：把整个 HUD 放进一个四边留白的容器内，宁可少一点可视面积，也不让控件压到挖孔 / 手势条 / 折痕。
4. **单画布 + 纯 UI 重排**：形态变化只触发 LayoutEngine 重排，不重建 Cocos 场景、不重载资源、不碰模拟状态（§8.1 C5）。

### 8.4 H1–H4 排期纪律（写进控制清单）

| 特性 | 档位 | 架构结论 |
| --- | --- | --- |
| H1 秒启卡片 | Could，只读不可操作 | 需卡片刷新通道 + 轻量数据投影；`IFeatureFlags` 预留，**须真机验证后方可排期**，不进 Must |
| H2 折叠屏双栏 | Should（平台特性优先级最高） | 降级路径（§8.3）已足以让首版跑通；**须真机验证后方可排期**，不进 Must |
| H3 跨设备流转 | Could | 数据层已预留接口位，但**不进排期**，理由见 §11.4 |
| H4 分布式多机同局 | **Won't** | 引入实时同步 / 权威状态 / 冲突消解，冲垮 lean 范围与概念 §2.3 排除项；架构不预留、不评估 |

## 9. 可访问性架构支撑（美术圣经 §9.2 Standard 级）

> 分级采用美术圣经 §9.1 的 **Standard 起步 / Comprehensive 升级**。架构提供的是「让 Standard 可落地且不可被性能降级误删」的支撑，不替 UX 规格（`design/ux/ux-spec.md`）定交互。

### 9.1 语义令牌单一映射（M14）

分区 / 状态先输出**语义令牌**（`zone.residential`、`status.congested`…），再由 `SemanticTokenMap` 统一映射为 **色值 + 图案 + 形状 + 文字标签 + 对比度校验结果**。渲染层与 UI 层都只查这张表：
- 分区 = 色 + 图案 + 文字三编码（色盲刚需）；状态 = 色 + 形状（✓/!/✕/锁/↑↓）。
- 全项目色值集中色板，禁止贴图内硬编码近似色（美术圣经 §3.5）。
- 对比度（正文 ≥4.5:1、大字 / 边界 ≥3:1）、去色 / 三型色盲模拟 → **纳入 CI 静态校验**（§13 G6）。

### 9.2 其余支撑

| 特性 | 架构支撑 |
| --- | --- |
| 文本缩放 100–200% | 系统缩放因子注入 LayoutEngine；弹性容器 / 自动换行，禁止固定宽高；文案容器按 1.5–2× 长度弹性（美术圣经 §7.3） |
| 动效可关 | `MotionPolicy` 全局策略，所有动效组件查询；即时反馈改瞬时静态（§7.4） |
| 触控热区 / 点击替代 | ≥44dp 热区 + 网格吸附；**输入抽象 / 命令别名**（同一 Command 可由点击、点击替代路径、未来键盘触发），UI 不假定输入源 |
| 多通道反馈 / 音频冗余 | 状态变化 ≥2 通道由语义令牌 + 事件广播保证；静音可完整进行（数值 / 图标 / 文字均在） |
| 字体 | 优先**系统字体**（HarmonyOS Sans）避免打包体积与授权风险；内嵌需先过法务（美术圣经 §7.2 / D-5、风险登记 R-08） |

### 9.3 「可访问性不降级」硬约束

美术圣经 D-8 明确：预算更紧时优先降级天气 / 粒子 / 夜间窗光，**不降级 §9.2 可访问性**。故 §9.1 的语义令牌、图案层、形状编码、热区、文本缩放、静态校验属于**硬约束层**，任何性能降级清单（§10.4）不得触碰；该条列为架构评审门 G6 的否决项。

## 10. 性能预算与真机校准计划（美术圣经 §9.4 建议基线 → 硬指标）

### 10.1 立场声明（硬约束）

> 美术圣经 §9.4 与本文出现的**所有性能数字均为建议基线，不是承诺值、不是已定指标**。本轮不把它们冻结为硬指标。下面给「如何转为硬指标」的实测方案（§10.3）；冻结动作发生在垂直切片可跑之后的第一次真机校准，并回写本文档。

| 指标 | 建议基线（来自美术圣经 §9.4，仅作测量起点） | 架构补充的测量口径 |
| --- | --- | --- |
| 目标帧率 | 30fps 稳定，复杂场景 ≥25fps | 测 p50 / p95 帧时间，不只测平均值 |
| DrawCall | L0 ≤30 / L1 ≤60–80 / L2 ≤120（平板折叠可 ≤150） | 按固定「基准城市场景」测，含合批是否生效 |
| 应用总内存 | ≤300–400 MB（中端机） | 常驻纹理 / 峰值 / 模拟数据分列 |
| 首包体积 | ≤150–200 MB，美术占比 ≤60% | 待 K-4 核对 HAP 上限后再定 |
| 常驻纹理内存 | ≤80–120 MB，峰值 ≤150 MB | 按 §6 分包实际加载量测 |
| **逻辑结算耗时（架构补充）** | **建议 p95 ≤ 16ms**（30fps 一帧 33ms 留一半给结算） | 单次 P0–P8 同步结算，测 32×32 满网格 |
| **「点按 → 可见反馈」链路（架构补充）** | **< 100ms**（美术圣经 §6.6） | 测达标率（%），不是测单次 |

### 10.2 有限网格规模上限与通勤图求解性能预算（概念 9.2 第 2 项 · 估算依据）

**规模结论（架构建议，交主理人确认后钉入 GDD）**：
- **逻辑网格固定 32×32 = 1024 格作为 MVP 硬上限**；起始解锁子集建议 16×16 = 256 格起步，按里程碑（OD-4 A）解锁至 32×32。
- 24×24 = 576 格为概念建议下界。**取 32×32 作上限**而非更大，依据见下四条；**扩到 >32×32 须重做通勤求解基准 + 快照体积评估**。

**通勤图求解估算（为什么它不是瓶颈）**：

| 量 | 估算 | 依据 |
| --- | --- | --- |
| 网格图节点 V | ≤ 1024（可通行格） | 32×32 上限 |
| 边 E（4 邻接） | ≈ 4V ≤ 4096 | 正交网格道路，上下左右连通 |
| 分区块 B（合并连续同类格为通勤源汇） | 保守 ≤ 64 | 典型 B ≈ N/16；**不做逐格 OD**（逐格会是 1024² 矩阵，必须合并分区块） |
| 单次多源最短路（无权 BFS） | B × O(V+E) ≈ 64 × 5120 ≈ **3.3×10⁵** 次边松弛 | 每个分区块一次 |
| 带权 Dijkstra（二叉堆） | B × O(E log V) ≈ 64 × 4096 × 10 ≈ **2.6×10⁶** 量级基本操作 | 若按通行时间加权 |
| 拥堵反馈迭代（MSA / Frank-Wolfe，4–8 次） | ×8 → **10⁷** 量级 | D2 拥堵负反馈需要迭代分配 |
| 移动端单次耗时（估） | 亚毫秒 ~ 数十毫秒 | 10⁵–10⁷ 次整数 / 浮点基本操作；**须实测确认**，不照抄为已定值 |

**关键结论**：
1. tick 是**玩家主动触发的一次性结算**（OD-2 A），不是每帧计算 → 通勤求解的 CPU 预算可比「每帧 16ms」宽松得多，但为「点按后无感」仍建议 p95 ≤ 16ms（§10.1）。
2. **瓶颈不在模拟，在渲染 / 图集 / 内存**（美术圣经 §9.4）：DrawCall、合批是否生效、常驻纹理、包体才是真机校准的重点；模拟数据只占几十 KB~几 MB（§4.3）。
3. 服务覆盖（P3）必须复用 P2 的通勤图结果，**禁止另起一套半径计算**，否则既破坏 P3 因果又浪费预算。

**网格上限 32×32 的四条依据**：
- ① 通勤求解 O(B×E) 随 N 线性（E≈4N），1024 格仍在 10⁵–10⁷ 量级可控；
- ② 权威状态 24–64 KB / 1024 格，快照与冷归档仅几 MB（§4.3）；
- ③ 128×64 @1x 下 L0 0.5× 全览需平移（等距投影宽 ≈ (32+32)×64 = 4096px，0.5× 仍 ≈2048px > 手机宽），相机须在固定角度内 pan、不引入自由旋转（概念 §7 锚点 1；与美术圣经 §2.2 的缩放档位存在口径冲突 X-4，见 §12）；
- ④ 概念 §5.1 明确「最终值由架构定」「Won't 无尽生成地图」，固定有限网格是 P2 机会成本成立的前提。

### 10.3 「建议基线 → 硬指标」五步实测方案

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 1 · 定基准场景 | 固定一份「基准城市」：32×32 满网格、L1 默认层、含拥堵链路 + 3 条议题 + 展开态布局；存档化，可重复加载 | 基准场景存档 + 加载脚本（后续实现） |
| 2 · 定机型矩阵 | 低 / 中 / 高档鸿蒙机 × 手机竖屏 / 折叠展开态 / 平板；含 1 台低档位机（验证降级档） | 机型矩阵表 |
| 3 · 采集 | DevEco Studio Profiler + Cocos Profiler + GPU 调试：帧时间 p50/p95、DrawCall、常驻 / 峰值内存、首包体积、单次结算耗时、冷启动时间、<100ms 反馈达标率、纹理格式探测结果（ASTC/ETC2）、合批是否生效 | 原始测量记录 |
| 4 · 逐条比对 | 每项「建议基线」与实测对比：达标 → 冻结为**硬指标**并回写本文；不达标 → 触发 §10.4 降级后复测；仍不达标 → 上报主理人裁定（降基线 or 砍特性） | 「建议 → 硬指标」校准报告 |
| 5 · 纳入回归 | 冻结后的硬指标进 CI 冒烟 / 真机回归门禁；引擎 / SDK 版本升级（§1.2 纪律 2）触发重测 | 门禁配置 |

**时机**：首个 Epic（垂直切片）可跑后、DoD 验收前做第 1 次校准（Story S-12）；**在此之前任何人不得把 §9.4 数字当承诺值对外 / 对内使用**。

### 10.4 降级顺序（不降可访问性）

## 11. 概念 §9.2 五项对齐 · 逐条可行性结论

> 主理人要求「逐条给可行性结论，不许只写待评估」。以下每条给 **结论动词 + 约束 + 实现建议 + 关联 ADR**。

### 11.1 【对齐 1】OD-2 A 主动推进制对模拟循环 / 存档 / 后台权限的约束 —— **结论：可行，且是架构最轻路径**

- **模拟循环**：改为「渲染帧循环 + 事件驱动一次性 tick 事务」双循环（§3.1）。模拟非循环、默认暂停、V6 触发；tick 间状态冻结。
- **存档**：存档退化为「自包含当前快照 + 可选命令溯源」（§5.1）；每次结算后原子落盘，`onBackground` 强制存一次；不需增量写优化。
- **后台权限**：**不需要**后台保活 / 精确闹钟 / 离线结算 / 时间同步 / 时钟防篡改（§5.2）；切后台只冻结 + 存一次，回来从快照恢复。
- **边缘情况实现建议**：暂停操作排队（CommandQueue，§3.1）、结算中重复点按由 InputGate 拒（§3.3）、切后台 / 折屏切换只冻结 + 重排不重置（§3.3 / §8.2）、倍速 Should 用 feature flag 且只是「定时产生 V6 命令」（§7.3）。
- **关联**：ADR-002、ADR-004。

### 11.2 【对齐 2】有限网格上限与通勤图性能预算 —— **结论：可行；32×32 定为 MVP 硬上限，通勤求解不是瓶颈**

- **规模**：钉 32×32 = 1024 格为上限，16×16 起步按里程碑解锁（§10.2）；>32×32 须重做基准。
- **估算依据**：V≤1024、E≈4V≤4096、分区块 B≤64，多源 BFS ≈3.3×10⁵、带权 Dijkstra ≈2.6×10⁶、含拥堵迭代 ≈10⁷ 量级基本操作 → 单次亚毫秒~数十毫秒（须实测）。
- **目标上限（建议，非承诺）**：单次 P0–P8 逻辑结算 p95 ≤ 16ms；「点按 → 可见反馈」<100ms（§10.1）。真正的瓶颈在渲染 / DrawCall / 内存，不在模拟。
- **实现建议**：合并分区块做 OD（禁止逐格矩阵）、P3 复用 P2 通勤图、确定性纯函数、零热路径分配（§2.2）。
- **关联**：ADR-002。

### 11.3 【对齐 3】折叠屏 / 平板双栏（H2）UI 框架能力与回退 —— **结论：有条件可行；降级路径已可支撑首版，H2 本身须真机验证后方可排期**

- **所需能力**：C1 安全区 insets 注入、C2 形态枚举 + 切换事件、C3 双栏容器（控显分离）、C4 弹性布局 / 文本缩放、C5 切换不重建场景不重置状态、C6 热区 / 输入抽象（§8.1）。
- **回退规则**：形态 → 布局映射表 + 回退状态机，未知 / 接口异常**统一回退 folded 单栏**；「功能不降级，只降信息密度增益」（§8.2）。
- **铰链 / 安全区接口不稳的降级**（4 条，§8.3）：启发式宽高比判形态（绕开 foldStatus）、读不到 insets 时「固定上下分栏 + 手动留白 24dp」、整体安全容器内缩、纯 UI 重排。
- **隔离价值**：一切系统能力经 PlatformAdapter 输出 LayoutProfile，UI 不碰 HarmonyOS API → 预览版接口变更只改一层。
- **纪律**：H2 是 Should、不进 Must、须真机（含折叠展开态）验证后方可排期。
- **关联**：ADR-001、ADR-004。

### 11.4 【对齐 4】跨设备流转（H3，Could）的同步前提，及为何 OD-2/OD-4 拍 A 后仍不宜进排期 —— **结论：技术上可实现，但收益 / 复杂度比不成立，明确不进排期**

**前提清单（若要开启，缺一不可）**：① 一个权威存档 + 单调 `tickId` / 版本向量；② 跨设备冲突检测与消解（两设备各自推进了 tick 怎么办）；③ `configHash` / `schemaVersion` 一致（两设备 App 版本漂移时快照不可互认）；④ 会话接管协议与目标设备完整状态重建；⑤ HarmonyOS 分布式 / 流转 API 在预览版的稳定性（K-2，须真机验证）。架构侧已在 `ISaveStorage` / 快照自包含 / 单调 tickId 上**预留接口位**（§5.4）。

**为何拍板 A 之后仍不宜排期（四条理由，逐条给结论）**：
1. **状态静止反而稀释收益**：OD-2 A（默认暂停、手动 tick、无现实时间推进）+ OD-4 A（固定有限地图）让状态是「静止、离散、可完全序列化的一坨快照」。玩家在 B 设备打开同一份存档即可续玩，本质是「多设备读同一份云存档」，**并不需要「会话流转」这种实时接管能力**——H3 的设计价值（手机起草 → 平板续做）依赖连续长会话，而拍板 A 的会话本就是「可随时放下的短快照」。
2. **引入本地单存档模型没有的复杂度**：同步会带出冲突消解、版本漂移、单调序号协调，而首版存档模型刻意保持单槽、无并发（§5.1）。为 Could 特性把核心存档复杂化，违背 lean。
3. **预览版 API 不稳 + 铁律**：H3 依赖的分布式 / 流转接口属 K-2 缺口，铁律规定「须真机验证后方可排期」「平台特性不进 Must」。
4. **与节奏定位冲突**：概念 §3.3 手机单次 5–12 min、Pastime 美学；跨设备续玩的长会话价值被削弱，且与概念 §9.1 R6「平台特性过度承诺」直接对冲。

> **一句话**：拍板 A 让「迁移」变得容易，却同时让「迁移」变得没必要；复杂度留给 Should/Could 的架构预留，不进排期。

### 11.5 【对齐 5】诊断面板 V2 的 tick 间指标差分 / 归因链快照策略（含回退复用） —— **结论：可行；采用「结算时记录归因 + Keyframe/Delta 快照」，回退即快照恢复**

- **差分**：P8 产出 Δ_t（逐指标旧 / 新 / 变化量 / 方向），UI 直接消费，不自行相减（§4.2）。
- **归因链**：由 P2~P5 **在结算中顺带记录**（`AttributionRecorder`），诊断面板**查询时只读、不重算模拟**（§4.2 三条理由：避免卡顿 / 避免配置漂移失真 / 保证 <100ms 响应）。
- **快照策略**：自包含 TickSnapshot（含 schemaVersion / configHash / engineVersion / PRNG seed / 命令溯源，§4.1）；保留策略 = **Keyframe（周期首 / 末全量）+ Delta（周期内差分与归因）+ 冷归档 ≥3 周期**（覆盖 D4「2~3 周期后浮现」），常驻内存 ≈1 MB 量级、冷归档 ≈3.2 MB 量级（§4.3 估算）。
- **回退重试复用快照**：因 `F` 确定性 + 命令溯源，**回退不需逆运算**，只需「重置到目标 keyframe、丢弃其后 delta、重新决策」；tick 级撤销与周期级重试（OD-1 A 未达标）同理，P7 只标记「可回退」不判负（§4.3）。
- **对 AC2 的保障**：任一满意度变化可追溯到 ≥1 条具体原因，数据层已具备（概念 AC2 / 9.1 R4）。
- **关联**：ADR-002、ADR-003。
