## 1. 背景（Context）

概念 §5.1 把存档 Must 钉为「**本地单存档 + 断点续玩**」，多存档位为 Should、跨设备流转（H3）为 Could 且「须架构确认」；§5.2 要求切片内「本地存档可断点续玩」。用户拍板 **OD-2 A**（默认暂停、手动 tick、无现实时间推进）与 **OD-1 A**（未达标可回退重试），使存档语义大幅简化；同时 **OD-4 A**（固定有限网格 + 里程碑解锁）要求解锁进度也进存档。

概念 §9.2 交给架构两项与本 ADR 直接相关：

- **第 4 项**：跨设备流转（H3，Could）的存档同步与状态一致性前提，及「为何在 OD-2/OD-4 拍板为 A 之后仍不宜进排期」。
- **第 5 项**：诊断面板所需 tick 间差分与归因链的**状态快照策略**（含回退重试如何复用快照）。

此外需处理：切后台写入中断 / 存档损坏、schema 演进、配置版本漂移、单机存档的安全定位、以及字体 / 资源授权对存档与包体的间接影响。

**知识缺口声明**：HarmonyOS 应用沙箱文件 / KV 偏好的确切接口、HAP 包体上限与权限模型（主文档 K-4）超出可确信范围；本 ADR 只钉「经 `ISaveStorage` 抽象 + 原子写语义」，不臆造具体 API。

---

## 2. 决策（Decision）

> **存档 = 自包含当前快照（含版本 / 配置 hash / 引擎版本 / PRNG 种子）+ ≥3 周期冷归档 + 校验和；采用「临时文件 → fsync → rename」原子写或 A/B 双槽；归因链「结算时记录、查询时只读、绝不重算」；MVP 仅本地单存档、断点续玩，不申请任何后台权限、不做离线结算；`ISaveStorage` 仅为 H3 预留能力位，本轮不实现任何同步逻辑、H3 不进排期。**

五条子决策：

1. **存档结构**（沿用 ADR-002 快照三件套，不另造格式）：
   ```
   SaveSlot = {
     header : { schemaVersion, configHash, engineVersion, saveTime(仅展示), checksum },
     current: 最近 Keyframe + 其后 Delta 链（或直接最近全量快照）,
     ledger : 最近 ≥3 周期冷归档（Keyframe + Delta，供诊断 / 回退）,
     prngSeed,
   }
   ```
   网格状态、预算、4 因子明细、议题、市民之声**引用 id**（OD-3 A：不做个体市民，文本正文不进存档结构）、解锁进度（OD-4 A）全部落在 `current` 与 `ledger`。

2. **OD-2 A 红利（明确写死）**：存档**不记录墙上时钟作为推进基准**、不需后台保活 / 精确闹钟 / 离线补算 / 时间同步 / 时钟防篡改。`saveTime` 仅作展示元数据，**不参与任何模拟计算**。切后台由 `ILifecycle.onBackground` 触发「冻结 + 存一次」，回来从最近快照恢复，无「补算漏掉的 tick」。

3. **落盘与完整性**：P8 每次提交后原子写；生命周期关键节点强制再存；关键操作（回退、解锁新区）后存。原子写用临时文件 + fsync + rename，或 **A/B 双槽**交替（任一时刻至少一个完好槽）。加载失败 / checksum 不符 / 版本不匹配 → 回退上一完好槽并提示；版本不匹配走**显式迁移器**，无迁移器则拒绝载入并保留旧槽，**禁止静默用新公式续算旧档**。

4. **归因只读**：Δ_t 与 `AttributionChain_t` 由结算 pipeline 产出并随快照落盘（ADR-002）；诊断面板 V2 **查询时只读**，不重跑模拟、不重算通勤求解。理由：避免卡顿、避免配置漂移导致历史结论失真、保证 <100ms 级响应（ADR-004）。

5. **安全定位（诚实标注）**：单机、无 PvP、无对抗（概念 §2.3 排除 Fellowship / Competition），checksum 用于**防误改 / 防写坏**，**不是反作弊、不是防篡改承诺**；不做强加密。若后续引入任何联网 / 排行特性，须另立安全 ADR 重新评估（本轮不预留）。

6. **H3 仅预留能力位**：`ISaveStorage` 接口签名预留「远端读写 + 版本向量」能力位，配合快照自包含 / 单调 `tickId` / `configHash`（ADR-002），使未来若开启 H3 不必重构数据层；**本轮不实现同步、不排期**（理由见 §4 第 4 项结论）。

## 3. 备选方案（Alternatives）

| # | 备选 | 描述 | 为何未选 |
| --- | --- | --- | --- |
| A1 | **只存当前状态，不存冷归档 / 归因链** | 存档最小 | 直接丢掉 V2 诊断与 D4 跨周期回溯、OD-1 A 回退重试、AC2 可追溯；与概念 §5.2「一次失败—诊断—修正—见效」冲突 |
| A2 | **纯命令日志（重放式存档）** | 只存命令序列，载入时从初始状态重放 | 启动慢、配置版本一变结论失真、无法 <100ms 响应诊断；ADR-002 A4 已否决，此处同理 |
| A3 | **云存档 / 跨设备同步（把 H3 做进首版）** | 存档上云、多设备续玩 | H3 为 Could 且铁律「须真机验证后方可排期、不进 Must」；引入冲突消解 / 版本漂移 / 预览版分布式 API 依赖，收益 / 复杂度比不成立（§4） |
| A4 | **归因在查询时重算** | 存档只存状态，诊断时重跑模拟解释 | 卡顿 + 配置漂移失真 + 违反即时性；ADR-002 A5 已否决 |
| A5 | **现实时间制存档语义**（记录墙上时钟、离线补算） | 回来补算漏掉的 tick | 已被 OD-2 A 否决；需后台权限 + 时钟基准 + 防篡改，与 Pastime 美学冲突；本 ADR 无权复议 |
| A6 | **强加密 / 防篡改存档** | 存档加密、校验签名、反作弊 | 单机无对抗、无 PvP（概念 §2.3），属过度设计；会被误读为安全承诺。改为轻量 checksum + 明确标注定位 |
| A7 | **多存档位 / 手动存读档进 Must** | 首版即做多槽 | 概念 §5.1 明确多存档位为 **Should**；首版只做本地单存档 + 断点续玩，不扩 Must（准入纪律） |
| A8 | **业务层直接读写文件路径 / 权限** | 绕过 `ISaveStorage` | 违反 ADR-001 平台隔离；预览版接口变更会波及存档；单元测试无法脱离设备 |

## 4. 概念 §9.2 第 4 项结论：为何 OD-2/OD-4 拍板为 A 之后 H3 仍不宜进排期

**可行性结论：技术上可实现（快照自包含、状态离散、单调 tickId 已具备迁移前提），但收益 / 复杂度比不成立，明确不进排期。**

**前提清单（若要开启，缺一不可）**：
1. 一个权威存档 + 单调 `tickId` / 版本向量（用于判定「谁更新」）；
2. 跨设备**冲突检测与消解**（两台设备各自推进了 tick 怎么办）；
3. `configHash` / `schemaVersion` 一致（两设备 App 版本漂移时快照不可互认）；
4. 会话接管协议与目标设备**完整状态重建**（依赖同版本配置表）；
5. HarmonyOS 分布式 / 流转 API 在开发者预览版的稳定性（主文档 K-2，须真机验证）。
> 架构侧已在 `ISaveStorage`、快照自包含、单调 `tickId` 上预留 1 / 3 的接口位，但 **2 / 4 / 5 均不实现**。

**四条理由（逐条给结论，不许「待评估」）**：

1. **状态静止反而稀释收益**。OD-2 A（默认暂停、手动 tick、无现实时间推进）+ OD-4 A（固定有限地图、里程碑解锁）让状态是「静止、离散、可完全序列化的一坨快照」。玩家在 B 设备打开同一份存档即可续玩，本质是「多设备读同一份云存档」，**并不需要「会话流转」这种实时接管能力**。H3 的设计价值（手机起草 → 平板续做）依赖**连续长会话**，而拍板 A 的会话本就是「可随时放下的短快照」——拍板 A 让「迁移」变容易，却同时让「迁移」变没必要。
2. **引入本地单存档模型本没有的复杂度**。同步会带出冲突消解、版本漂移、单调序号协调，而首版存档刻意保持单槽、无并发。为 Could 特性把核心存档复杂化，违背 lean 与概念 §9.1 R6（平台特性过度承诺）。
3. **预览版 API 不稳 + 铁律约束**。H3 依赖的分布式 / 流转接口属 K-2 缺口；主理人硬约束规定「任何平台特性须真机验证后方可排期」「H1/H2/H3 一律不进 Must」。未真机验证前排期即违规。
4. **与节奏定位冲突**。概念 §3.3 手机单次 5–12 min、Pastime 美学「可随时放下」；跨设备续玩的长会话价值被削弱，且与「不为覆盖而塞系统」的范围纪律（概念 §2.3 / §4.2）相悖。

> **一句话**：复杂度留给 Should/Could 的**架构预留**（接口位 + 自包含快照 + 单调 id），不进排期、不进 Must、不实现同步代码。

---

## 5. 理由（Rationale）

1. **合规**：存档 Must 严格等于概念 §5.1「本地单存档 + 断点续玩」，未擅自升级为云存档 / 多槽。
2. **OD-2 A 的最大架构红利被吃满**：消除后台权限、离线结算、时间基准、时钟防篡改整块复杂度；tick 稀疏使「每次结算后落盘」开销可忽略。
3. **一份数据多处复用**：同一份快照 / Δ / 归因链服务 UI、诊断、存档、回退、未来迁移，杜绝重复实现与数值不一致。
4. **AC2 / D4 的持久保障**：归因与 ≥3 周期冷归档落盘，使「跨会话、跨周期的满意度变化」仍可追溯（概念 9.2 第 5 项后半「回退重试如何复用快照」也依赖此）。
5. **回退几乎免费**：OD-1 A 的「未达标可回退重试」= 恢复周期起始 Keyframe + 丢弃其后 Delta（ADR-002），存档只需保存 Keyframe 即可支持。
6. **诚实的安全定位**：单机无对抗，checksum 只防写坏；不制造「我们做了反作弊」的误解。

## 6. 后果（Consequences）

**正面**
- 存档实现薄、可全量单测 + 故障注入（写中断 / 损坏 / 版本不匹配）；CI 无需真机。
- 断点续玩、切后台恢复、回退重试、跨周期诊断共用一套数据，一致性由结构保证。
- 不申请后台权限 → 权限声明最小，降低 K-4（权限模型未知）带来的上架风险。
- 未来若开启 H3 / 多存档位，只需扩 `ISaveStorage` 实现与迁移器，数据层不重构。

**负面 / 成本**
- 存档自包含（版本 / hash / seed / 命令溯源）+ 冷归档使单文件比「存个状态对象」大（估算冷归档 ≈3.2 MB 量级，主文档 §4.3），需内存 / 落盘水位监控。
- 需要维护 `schemaVersion` 迁移器与「拒绝载入旧档」的用户提示路径；版本纪律变严。
- 单槽 + 每次提交原子写，写失败时依赖 A/B 双槽兜底，需故障注入测试覆盖。
- 明确「不做强加密」意味着存档可被用户手工修改；这是单机取捨，须在文案 / 说明中避免暗示防篡改。

**中性 / 边界**
- 具体存储接口（应用沙箱文件 / KV 偏好）、HAP 权限模型待真机核对（K-4）。
- 字体（HarmonyOS Sans 打包 / 商用、思源黑体 OFL）属**法务 + 架构**风险（美术圣经 D-5），与存档无关但进包体 / 授权风险登记 R-08；架构优先系统字体引用。
- 市民之声文本正文属文案资产，存档只存引用 id（OD-3 A），不做个体市民数据。
