## 1. 背景（Context）

### 1.1 官方约束

`AC-A10-1` 取自华为《通用应用 UX 体验标准》**2.1.3.4**，标准等级**必须**：**用户主要交互的滑动控件高度 ≥ 屏幕高度的 20%**。本项目取官方条文原义，不自行放宽。

### 1.2 现行比例与「算术死结」

只读实测 `src/ui/hud/layout-profile.ts` `segmentRatios()`（2026-11-07）：

| 形态 | statusBar | canvas | thumbZone | 常驻覆盖 `statusBar + thumbZone` |
| --- | --- | --- | --- | --- |
| `folded`（折叠） | 0.12 | 0.70 | 0.18 | 0.30（贴线） |
| `tablet`（平板） | 0.10 | 0.78 | 0.12 | 0.22 |
| `default`（手机） | 0.13 | 0.69 | 0.18 | **0.31（越线）** |

两条结论：

1. **除 `canvas` 外无任何一段 ≥ 20%**。`canvas` 虽 69–78%，但它是**只读地图画布**（C3 控显分离：上只读、下交互），不承载「滑动控件」，不能用来顶 `AC-A10-1`。
2. **算术死结**：若 UX 把任一滚动容器（诊断面板滚动区 / 议题列表 / 预算滑块）指派进 `thumbZone` 并要求其高度 ≥20% 屏高 → `0.18 < 0.20`，在现行 `segmentRatios` 下**不可能达标**。这不是「待测」或「待实测」，是**已知条件下必然不达标**。

### 1.3 本 ADR 顺带修掉的既有违规

`statusBar + thumbZone`：手机 `0.13 + 0.18 = 0.31 > 0.30`，已违反 `art-bible §2.4`「**UI 常驻覆盖率 ≤ 30%（手机竖屏）**」；折叠 `0.12 + 0.18 = 0.30` 恰在线上。

由此得出一条硬约束：**不能只抬 `thumbZone` 不压 `statusBar`**——`0.13 + 0.20 = 0.33`、`0.12 + 0.20 = 0.32`，两形态都会破 30% 上限。抬 `thumbZone` 必须与压 `statusBar` 同批发生，否则等于用手布局换破构图约束。

---

## 2. 决策（Decision）

> **三形态统一为 `statusBar 0.10 / canvas 0.70 / thumbZone 0.20`**；常驻覆盖率 `statusBar + thumbZone = 0.30`，三形态齐平于 `art-bible §2.4` 的 30% 上限，**不再有一处越线**。

| 形态 | 原比例 | **新比例** | 常驻覆盖 | `canvas` 变化 |
| --- | --- | --- | --- | --- |
| `default`（手机） | 0.13 / 0.69 / 0.18 | **0.10 / 0.70 / 0.20** | 0.30 ✓（原 0.31 越线） | 0.69 → 0.70（**+0.01，增大**） |
| `folded`（折叠） | 0.12 / 0.70 / 0.18 | **0.10 / 0.70 / 0.20** | 0.30 ✓（原 0.30 贴线） | 0.70 → 0.70（不变） |
| `tablet`（平板） | 0.10 / 0.78 / 0.12 | **0.10 / 0.70 / 0.20** | 0.30 ✓（原 0.22） | 0.78 → 0.70（**−0.08**） |

三条附注：

1. **`thumbZone 0.20` 是「算术前置」，不是「达标」**：它为 `AC-A10-1` 预留了可成立的数学空间，但能否达标取决于是否真有滑动控件、以及 UX 给它的占屏比（§5 边界声明）。
2. **`statusBar 0.10` 不降低其最小高度**：`MIN_STATUS_DP = 48dp` 的**地板不变**，占比下调只削减大屏富余量；顶部仅承载「≤3 全局指标 + 只读状态条」（概念 §3.3 硬上限），48dp + 系统缩放注入即够。
3. **实现要求（交代码专流）**：`heightRatio` 是**声明数据**，实际段高须按 `max(minHeightDp, heightRatio × 可用高度)` 夹取。现状 `layout-profile.ts` **无 clamp**（文件内无 `Math.max` / clamp 逻辑，`minHeightDp` 仅作为声明值被 `assertTextScaleLayout` 消费），故本 ADR 只钉声明值，夹取语义列为落地验收项（§7 A3）。

## 3. 备选方案（Alternatives）

| # | 备选 | 描述 | 为何未选 |
| --- | --- | --- | --- |
| A1 | **允许滑动控件跨出 `thumbZone` 边界** | 控件高度不受段高限制，视觉上覆盖画布 | 破坏 **C3 控显分离**（上只读画布 / 下交互区）与**三段 id 恒定**（`layout-profile.ts` 头注「跨重排不变」）；控件压到地图上还会破 `art-bible §2.4`「选中地块周围 ≥1 格视觉留白、禁止被常驻面板压住」 |
| A2 | **证成「不适用」即可** | 当前无滑动控件，不必改布局 | **保留为并行结论**（§5 边界），但**不作为唯一处置**：将来一旦新增滚动容器就立刻撞回同一个死结，等于把问题推给未来且没有预警 |
| A3 | **维持现状，台账记「不达标」** | 文档侧只记录、不动比例 | 否决。等于承认一个**已知的算术死结**不修；且现状还叠加了 `0.31 > 0.30` 的构图违规，放着不改没有任何收益 |
| A4 | **只抬 `thumbZone`，不动 `statusBar`** | 最小改动 | 否决。`0.13 + 0.20 = 0.33`、`0.12 + 0.20 = 0.32` 均破 30% 上限，属「用手布局换破构图约束」，不可接受 |
| A5 | **抬 `thumbZone` 并压 `canvas`** | 把压力全给画布 | 否决。`canvas` 是主视觉重心（`art-bible §2.4`「中央画布保持最大连续可见面积」）；且压缩画布会直接损害 V3/V4/V5 的地图操作精度与选中态留白 |

## 4. 理由（Rationale）

1. **双约束同时守住**：`thumbZone` 达标前置（0.20）与常驻覆盖上限（0.30）在同一次改动内同时成立，不存在「修一个破一个」。
2. **顺带修掉既有违规**：手机 `0.31 > 0.30` 是**改前就存在**的问题，本 ADR 把它一并对齐到 0.30，三形态不再有越线项。
3. **手机侧画布反而变大**：手机 `canvas 0.69 → 0.70`，主视觉面积净增，属正向收益。
4. **声明与实现分离**：本 ADR 只改 `LayoutProfile` 的**声明比例**，不改任何渲染 / 命中 / 断言代码，故不引入运行时风险；代码同步由专流处理（§6 R-4）。
5. **可无损回退**：比例是纯数据，回退即改回原值，不涉及存档、快照、schema 迁移（对比 ADR-002/003 类改动的代价低一个量级）。

## 5. 后果（Consequences）

**正面**
- `thumbZone` 达 20%，消除「将来加滑动控件必然不达标」的前置障碍。
- 常驻覆盖三形态统一 0.30，手机越线违规被修掉。
- 手机 `canvas` 净增 0.01；折叠不变。
- 三段结构、id 恒定、C3 控显分离、C5 形态切换不重建场景**全部不变**（本 ADR 只改数值）。

**负面 / 成本**
- **平板 `canvas` 0.78 → 0.70（−0.08，相对减少约 10%）**：地图可见面积缩小。平板属 H2 Should 级平台特性、不进首版 Must，故不阻塞首版；但启用平板双栏时须真机复核小地图、选中态放大反馈与 ≥1 格留白是否仍成立。
- 手机 / 折叠 `statusBar` 减少 0.02~0.03：大屏富余量下降，`MIN_STATUS_DP = 48dp` 地板不变，低分辨率设备需真机确认「≤3 指标 + 状态条」不挤。
- `MIN_CANVAS_DP = 240` 的保护性质要写清：它是**声明地板**，不是运行时夹取。平板 `canvas` 要跌破 240dp 需可用高度 `< 240 / 0.70 ≈ 342.9dp`（原 0.78 时为 `307.7dp`）——现役目标机可用高度远高于此，故比例下调**不触破**该地板；真正的风险是缺 clamp（§6 R-3），不是比例本身。

**中性 / 边界（必须明确写住）**
- **本 ADR 不使 `AC-A10-1` 变为通过。** 本项目当前**无任何滑动控件实例**：`src/` 全仓与滑动相关的仅 `scrollY` 一个状态字段（`createLayoutState`），`ux-spec` / 5 份系统 GDD 内「滑块 / 滑动 / slider / 拖动」零命中。故该条判定状态记为**「不适用（无适用对象）」**，并带条件重开：UX 交付《滑动控件清单》（控件 id × 所属槽位 × 占屏比 × 是否承载主要交互）中确有对象落入任一槽位时，本条即重开并按「≥ 屏高 20%」判。**N/A ≠ PASS**——N/A 不计入「通过」分子，任何汇总不得把 N/A 与 PASS 合并计数，**不得据此宣称「29 条 AC 全通过」**。本 ADR 只消除「将来新增滚动容器即撞回算术死结」的前置障碍。
- 本 ADR 不定义滑动控件的**身份与归属槽位**——那属 UX《滑动控件清单》（S-12 门禁输入前置：控件 id / 所属槽位 / 占屏比 / 是否承载主要交互）。清单未出前，本 ADR 的收益停留在「预留空间」层面。

## 6. 风险（Risks）

| # | 风险 | 触发信号 | 影响 | 缓解 | 责任侧 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| R-1 | 平板画布变小影响操作 | 平板双栏启用后小地图 / 选中态被压、留白不足 1 格 | V3/V4/V5 精度与可读性下降 | 平板属 H2（Should、不进 Must）；启用前真机复核；必要时平板单独回退 0.78 并在此处登记例外（须主理人确认） | 架构 / UI / 美术 | 平板真机截图回归 |

| R-4 | **文档-代码不一致窗口**（**2026-11-07 已关闭**，本行保留为决策当时的风险记录） | 本 ADR 已改声明值，`layout-profile.ts` 仍是旧比例〔**状态更新**：代码已落地 `UNIFIED_SEGMENT_RATIOS = 0.10/0.70/0.20`，`layout-profile.ts:60`，见文末落地回执〕 | 读者据文档误判现状 | **代码未同步前，比例一律以代码为准**〔已同步，此条不再生效〕；台账单列该不一致，代码同步后关闭 | 架构 / 布局实现 | 同步后 `grep` 比例 + 单测〔已完成：`hud-layout.test.ts` LAY-7 按新不变量改写 + `move` 分支合成模型覆盖，全量 571/569/0/2〕 |
| R-5 | 200% 文本缩放下地板与占比冲突 | `minHeightDp × 2` 合计 704dp（≤ `REFERENCE_HEIGHT_DP` 800dp，断言仍过），但 `canvas` 地板升至 480dp，`0.70 × 可用高度` 在 568dp 级设备上只有约 398dp → **clamp 会触发并挤压其它段** | 高缩放下可能靠 clamp 保画布、代价是别的段 | 这是**改前既存**的张力（`MIN_CANVAS_DP` 与 200% 缩放的组合），非本 ADR 引入；真机复核 200% 下三段实际分配，必要时登记例外 | 可访问性 / 布局 | 200% 文本缩放真机回归 |

> **数字立场**：本 ADR 的比例是**已决策的声明值**（用户 2026-11-07 拍板），不是「建议基线」；但 `MIN_*_DP` 地板与 clamp 语义的**实际生效**须真机与落地断言共同确认。
