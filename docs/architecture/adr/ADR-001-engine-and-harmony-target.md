## 1. 背景（Context）

用户已拍板且不可复议：平台为 **HarmonyOS 7（开发者预览 / SDK 26 / API 26）**、手机竖屏优先兼容平板折叠屏；引擎链路为 **Cocos Creator 3.x 官方适配 HarmonyOS NEXT → 导出 HarmonyOS 工程 → DevEco Studio 打包 HAP**；形态为 2D 管线 + 2:1 dimetric 等距（128×64 格）、低频 tick、网格地图、密集 UI。

本 ADR 需要解决的**不是**「选哪个引擎」（已拍板），而是三个尚需架构定钉的问题：

1. **工程链路的职责边界**：Cocos 导出物与 DevEco 工程里，哪些是「真源」、哪些是「构建产物 / 胶水」；游戏规则写在哪一层。
2. **Node-API / XComponent 边界**：ArkTS 应用层（系统能力所在）与 Cocos 脚本层（游戏规则所在）如何桥接，才能做到「游戏逻辑零 HarmonyOS SDK 依赖」。
3. **预览版 API 不稳定的隔离**：折叠态 / 安全区 / 避让区 / 多窗口 / 分布式接口在开发者预览版可能改名、改行为甚至不可用（美术圣经 D-2 / 概念 9.2 第 3 项），架构必须让这类变化**只影响一层**，不波及模拟、快照、存档格式。

同时需承接硬约束：H1/H2/H3 不进 Must、H4 Won't、任何平台特性须标注「须真机验证后方可排期」。

**知识缺口声明**：Cocos 支持 HarmonyOS NEXT 的确切小版本、导出工程结构、NAPI 桥实现细节、API 26 预览版折叠 / 安全区接口名，均超出可确信范围（主文档 K-1/K-2）。本 ADR 只钉「能力类别 + 抽象接口 + 隔离原则」，**不臆造具体 API 名称**。

---

## 2. 决策（Decision）

> **采用 Cocos Creator 3.x → HarmonyOS NEXT 导出 → DevEco Studio 打包 HAP 的链路；把全部 HarmonyOS 系统能力封装进引擎脚本侧的单一「平台适配层 PlatformAdapter」，经 NAPI/XComponent 与 ArkTS 应用层桥接；业务层（数据 / 模拟 / 渲染 / UI）只见稳定抽象接口，零 HarmonyOS SDK 依赖。**

具体四条：

1. **单一真源**：游戏逻辑（TS）、场景、图集、配置表只在 Cocos 工程侧维护；HarmonyOS 工程骨架 = 构建产物 + 极薄平台胶水（UIAbility / XComponent / NAPI 注册 / 权限声明）。**禁止在 ArkTS 层写任何游戏规则**。
2. **桥接边界**：ArkTS 层持有 UIAbility 生命周期、XComponent(Surface)、window / 安全区 / 折叠态、文件沙箱、无障碍、系统字号、以及 H1/H3 的能力位；经 NAPI 注册与事件转发到 PlatformAdapter；Cocos 用 XComponent 的 Surface 建 EGL 上下文渲染 2D 场景。
3. **抽象接口（业务层唯一可见面）**：`ILifecycle`、`IWindowInsetProvider`、`IFoldStateProvider`、`ISaveStorage`、`IAccessibilityBridge`、`IFeatureFlags`。适配层把系统原语转换为稳定数据结构（`LayoutProfile`、安全区 insets、系统缩放因子、形态枚举）后向下分发。
4. **不用 ArkUI 拼游戏 UI**：HUD / 议题 / 诊断面板 / 建造 Tab 全部在 Cocos 场景树内绘制，避免两套 UI 状态、两套安全区、两套动效策略；ArkUI 只承载宿主容器与（H1 若做）桌面卡片。

**版本纪律**：Cocos 小版本 / HarmonyOS SDK·API / DevEco Studio 版本三者写入构建锁并纳入真机回归；任一升级重跑性能校准（`architecture.md` §10.3）。

## 3. 备选方案（Alternatives）

| # | 备选 | 描述 | 为何未选 |
| --- | --- | --- | --- |
| A1 | **原生 ArkTS + ArkUI 全自研**（不用 Cocos） | 全部 UI 与 2D 渲染用鸿蒙原生能力自研 | **直接违背用户已拍板前提**（Cocos 3.x 适配链）；等距 tile 合批 / 图集 / UI 密集场景需自建引擎能力，lean 范围不可承受；无 2D 生态积累 |
| A2 | **Unity / Godot 4 替代 Cocos** | 换用其他引擎的鸿蒙导出能力 | 同样**违背已拍板前提**；且用户钉的是「Cocos 3.x 官方适配 HarmonyOS NEXT」，改引擎属支柱级改动，须回用户拍板（概念 §0.1 / §10.3） |
| A3 | **业务层直接调用 HarmonyOS SDK**（不设适配层） | 模拟 / UI 里直接 import 系统 API 取安全区、存文件、读折叠态 | 预览版 API 一变，游戏规则与快照格式连带改；单元测试无法脱离设备运行；H1~H3 特性会渗进 Must 层。**隔离成本远低于耦合成本**，否决 |
| A4 | **Cocos 引擎 C++ 层直接做平台能力** | 把安全区 / 文件 IO / 分布式写进 native 层，跳过 ArkTS | 系统能力（尤其 window / 分布式 / 卡片 / 无障碍）本就在 ArkTS 框架层，native 直取会绕开权限与生命周期模型；且引擎升级时 diff 巨大、不可维护 |
| A5 | **游戏 UI 用 ArkUI、世界用 XComponent 混合** | 双 UI 栈 | 两套安全区 / 两套文本缩放 / 两套动效策略 / 两套状态同步，直接冲垮 §9.2 可访问性一致性与 <100ms 反馈（ADR-004）；否决 |

> 说明：A1/A2 属「突破已拍板前提」，本 ADR 无权选择，仅列出以完整记录决策空间。

---

## 4. 理由（Rationale）

1. **合规**：完整承接用户四条已拍板前提，不复议、不越界。
2. **2D 等距最经济**：Cocos 3.x 2D 管线对 128×64 等距 tile、图集合批、密集 UI 支持最成熟，资产只需一套朝向（美术圣经 §2.1 / C-2 / §9.3），与 lean 范围一致。
3. **预览版风险的唯一可行解**：开发者预览版 API 不稳定是**确定性事实**（K-2）。把系统能力压到单一适配层，是把「不可控的外部变化」转成「可控的内部接口变更」，这正是概念 9.2 第 3 项要的降级能力（主文档 §8.3）。
4. **可测性**：模拟 / 数据 / 存档逻辑运行在纯 TS、零系统依赖，可全量单测与离线回放（ADR-002 的确定性前提），不必挂真机。
5. **平台特性纪律落地**：H1/H2/H3 的能力位只在适配层开 `IFeatureFlags`，默认关、须真机验证后方可排期；H4 不预留、不评估。

## 5. 后果（Consequences）

**正面**
- 业务层与平台解耦：API 26 接口改名 / 行为变化只改 PlatformAdapter 一处，规则、快照、存档格式零改动。
- 首个 Epic 对 H1–H4 **零阻塞**：只走适配层的稳定接口与降级默认值即可在手机竖屏跑通垂直切片（G12）。
- 单元测试可脱离真机运行；CI 可跑模拟 / 存档 / 归因的黄金路径。
- 未来若开启 H2/H3，只是扩适配层实现，不重构数据层（ADR-003 §5.4 预留）。

**负面 / 成本**
- 多一层接口定义与胶水代码（一次性成本）；NAPI 桥的构建与调试链路较纯移动端复杂。
- 引擎导出的工程骨架是「半黑盒」，版本升级需重跑回归；必须靠构建锁与校准报告约束。
- 适配层若设计不当易变成「大杂烩」→ 用 §2 的六个接口 + 单一输出类型（LayoutProfile / insets / 缩放因子 / 形态枚举）约束其边界。

**中性**
- 具体 API 名称、导出目录结构、签名权限模型在真机跑通前保持未知（K-1/K-4），以「能力类别」占位，不写进任何业务代码。

## 6. 风险（Risks）

| # | 风险 | 触发信号 | 影响 | 缓解 | 责任侧 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| R-1 | 预览版 API 不稳定（折叠 / 安全区 / 避让区 / 多窗口 / 分布式接口） | 接口改名、返回值结构变化、编译失败、真机与文档行为不符 | 适配层返工；若耦合到业务层则会波及快照 / 存档 | 全部系统能力只在适配层；降级路径（启发式宽高比判形态、手动留白 24dp、整体安全容器内缩）先实现并验证 | 架构 / 平台适配 | 折叠展开态真机冒烟（S-01 / S-08） |
| R-2 | Cocos 鸿蒙导出成熟度 / 确切小版本未知 | 导出失败、NAPI 桥缺失、Surface 无法建 EGL、脚本虚拟机性能异常 | 工程链路不成立 | 先跑「空场景 + 生命周期切换」最小验证（S-01）；锁定版本组合后冻结 | 架构 | DevEco 真机启动空场景 |
| R-3 | 纹理压缩 / 合批 / 后处理支持未验证（ASTC / ETC2） | 导出后图集模糊、DrawCall 高于基线、Shader 变体报错 | 性能基线不达标 | 格式能力探测 + ASTC→ETC2→RGB565 降级；同图集同材质合批；不引入逐对象材质（主文档 §6.3） | 架构 / 美术 | 真机 Profiling（§10.3 第 3 步） |
| R-4 | 引擎 / SDK 版本升级打破可复现构建 | 升级后旧快照回放结果不一致、帧率漂移 | 存档兼容性与性能承诺失真 | 构建锁 + 快照内 `engineVersion` / `configHash`；升级强制重跑校准（§1.2 纪律 2） | 架构 / DevOps | 版本升级回归清单 |
| R-5 | 适配层膨胀成「什么都能调」的后门 | 业务层出现绕过接口直连系统能力的 import | 隔离失效，R-1 风险回归 | 代码评审门 G2 否决项 + 静态检查「业务层 import 白名单」 | 架构 / 主程 | 结构检查（G2） |
| R-6 | HAP 包体 / 权限模型未知（含后台权限误申请） | 打包超限、误声明后台保活权限 | 上架受阻 / 违背 OD-2 A 轻架构 | 待测；**OD-2 A 下不申请任何后台权限**（ADR-003 §5.2）；优先系统字体（美术圣经 D-5） | 架构 / DevOps | 打包与权限声明核对 |

## 7. 验收（Acceptance）

| # | 验收条件 | 证据路径（后续实现阶段产出） |
| --- | --- | --- |
| A1 | Cocos 3.x 工程可导出 HarmonyOS NEXT 工程，DevEco Studio 可编译签名产出 HAP，真机（手机竖屏）启动空场景成功 | S-01 构建记录 + 启动截图 / 日志 |
| A2 | XComponent Surface 正常渲染 2D 等距网格；`onForeground/onBackground`、surface 销毁重建、折叠态切换均不崩溃、不重置模拟状态 | S-01 / S-08 生命周期冒烟记录 |
| A3 | 静态检查：业务层（数据 / 模拟 / 渲染 / UI）**零** HarmonyOS SDK / ArkTS import；系统能力调用 100% 经 PlatformAdapter 的六个接口 | 代码评审门 G2 检查记录 |
| A4 | 折叠态 / 安全区接口**读取失败**时，降级路径生效：回退单栏布局、24dp 留白、关键控件不压铰链带，V1–V9 仍完整可达 | 折叠展开态真机回归（S-08） |
| A5 | 版本锁文件存在，且 `engineVersion` / `configHash` 写入存档头（与 ADR-003 联验） | 构建锁 + 存档 schema 单测 |
| A6 | H1/H2/H3 的能力位默认关、H4 无实现；文档与代码中均无平台特性进入 Must 的路径 | G8 自检 + feature flag 配置核对 |

> **验收门槛说明**：A1/A2/A4 属「须真机验证后方可排期」类，验证的是**引擎链路与降级路径本身**，不是实现 H1/H2/H3 特性；未通过前不得把任何平台特性排进 Must。
