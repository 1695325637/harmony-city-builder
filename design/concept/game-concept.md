## 1. 一句话概念与设计支柱

### 1.1 一句话概念

> **在有限的土地与一份必须月月结平的市政预算里，通过分区规划与交通组织持续提升市民满意度——你造的不是天际线，是一座让人愿意留下来的现代城市。**

补一句定位句，用于对外/对内统一口径：
**「把城建从『造得宏大』转向『算得清楚』，一款能在通勤路上打完一个市政周期的现代都市经营游戏。」**

### 1.2 设计支柱（4 条，每条附否决项）

支柱不是口号，是**否决权**。后续任何系统提案若命中某条支柱的「否决」列，默认不予立项。

| # | 支柱 | 具体含义 | **这条支柱会否决哪些设计** |
| --- | --- | --- | --- |
| **P1** | **满意度是唯一计分板** | 城市好不好，市民说了算。人口、产值、建筑数都只是**过程量**，最终都折算进满意度；不设第二条并列终局指标 | ① 纯人口/GDP/地价排行榜；② 「建得越多得分越高」的建造奖励；③ 以建筑数量或城市面积为胜利条件；④ 与满意度并列且互不折算的「第二终局轴」（如独立财政评分） |
| **P2** | **每一笔投入都有机会成本** | 土地有限、预算有限、每栋建筑有持续维护费；「不建什么」和「建什么」同等重要 | ① 无限资源/零成本沙盒作为默认模式；② 建成即永久生效、无维护费、无衰退的被动收益建筑；③ 任何场景通用的「万金油最优解」；④ 不消耗土地或不占预算的免费扩张 |
| **P3** | **城市是流动系统，不是静态截图** | 满意度由**通勤链路**与**时间推移**共同决定；分区的价值取决于它连到哪里，而非它旁边是什么 | ① 只按静态半径叠 buff 的邻接系统；② 忽略通勤路径的服务覆盖算法；③ 瞬时结算、无时间维度的建造反馈；④ 可绕过交通网络的传送式服务/一键全覆盖 |
| **P4** | **拇指宽的决读优先** | 手机竖屏上一次决策应在 **30 秒内读懂、一次点按完成**；密集 UI 必须分层，不能摊在同一屏 | ① 需要多窗口并行比对或精确微操的交互；② 以密集数值表格作为主交互面；③ 必须长时间在线挂机才能推进的核心循环；④ PC 式快捷键/悬浮多面板依赖；⑤ 任何要求玩家「记住跨屏数据」的机制 |

### 1.3 支柱漂移预警（设计红线自检）

在后续每一份系统 GDD 评审时，逐条对照以下 4 个漂移信号，命中即标注退回：

- **P1 漂移**：出现「人口里程碑奖励」「建筑面积成就」等未折算进满意度的独立激励。
- **P2 漂移**：出现「免费地块」「零维护地标」「一建永逸」等削弱机会成本的提案。
- **P3 漂移**：出现「半径内即覆盖」「即时生效」等把系统压回静态的做法。
- **P4 漂移**：一个屏幕同时出现 2 个以上数据面板，或单次决策需要跨 3 层菜单。

## 2. MDA 框架分析

### 2.1 规则（Rules / Mechanics）

约束来自已拍板技术路线：低频 tick、网格地图、密集 UI。规则层只列**机制事实**，不列数值。

| 规则 | 说明 | 服务的支柱 |
| --- | --- | --- |
| R1 有限网格 | 城市建在固定尺寸网格上，地块是稀缺资源；新区需按里程碑解锁 | P2 |
| R2 分区类型 | 玩家在地块上指定分区（**居住 / 商业 / 产业 3 类**），建筑按分区 + 密度生长，玩家不逐栋摆楼；公共服务分区属 Should 期扩展，不在 MVP | P4, P2 |
| R3 市政预算 | 每个结算周期有收入、建设支出、持续维护费、结余；结余可结转但不可透支无代价 | P2 |
| R4 交通网络 | 道路构成通勤图；分区之间通过网络产生流量，通行能力有限 | P3 |
| R5 低频 tick | 模拟按离散 tick 推进（1 tick = 1 游戏日），tick 之间城市状态冻结、玩家可从容决策；**默认暂停、玩家点「结束本日」结算一次（OD-2 A 已拍板）** | P3, P4 |
| R6 满意度合成 | 市民满意度由多因子合成，**因子清单锁定为 4 项**：`通勤时长`、`服务覆盖`、`环境负荷`、`财政投入` | P1 |
| R7 时间/周期 | tick 累积成「市政周期」，周期末做一次预算结算与目标判定 | P1, P2 |
| R8 状态可读 | 任一时刻玩家可查询「当前议题」及「指标变化的原因」（诊断面板） | P4 |

> **边界声明**：R6 只锁定**因子清单**，刻意不定义公式与权重。满意度 = f(通勤时长, 服务覆盖, 环境负荷, 财政投入) 中各变量的定义、单位与权重属于系统 GDD 职责，本阶段不越界定稿，以免把概念期的直觉数值当成平衡基线。
> **v1.0 一致性修正**：R2 原列 4 类分区（含公共服务），与 5.1 MoSCoW 的「3 类 Must + 公共服务 Should」及 OD-4 A 的垂直切片口径不一致，现统一为 3 类。此为文字收敛，不改变设计结论。

### 2.2 动态（Dynamics · 运行时会自然发生什么）

| 动态 | 因果链 | 对玩家的意义 |
| --- | --- | --- |
| D1 通勤潮汐 | 居住区与产业区错配 → 高峰流量集中 → 通勤时长上升 → 满意度下降 | 「位置比数量重要」，逼出规划而非堆料 |
| D2 拥堵负反馈 | 路网容量饱和 → 服务抵达变慢 → 覆盖因子恶化 → 满意度下滑 | 让玩家必须回头改路网，形成二次决策 |
| D3 预算剪刀差 | 扩张带来新建筑 → 维护费阶梯上升 → 收入却随满意度滞后变化 → 短期财政吃紧 | 制造「先发展还是先固本」的节奏张力 |
| D4 滞后暴露 | 分区决策的负面后果不在当 tick 显现，而在 2~3 个周期后浮现 | 需要诊断与复盘，撑起 Explorer 型玩法 |
| D5 救火—规划交替 | 玩家在「处理已暴露议题」与「提前布局新区」之间往复 | 构成中循环的节奏脉冲（见 3.3） |
| D6 满意度—收入回路 | 满意度影响收入 → 收入约束下一轮投入 → 投入再影响满意度 | 主反馈回路；**必须设计为软着陆，不可做成不可逆死亡螺旋**（见 9.1 R5） |

> **v1.0 范围澄清**：3.3 / 4.3 中的「危机脉冲」（预算吃紧、通勤拥堵爆发）指 D2 / D3 等**系统自然波动**，不设立独立的「危机事件系统」——后者属 5.2 切片外明确不做的内容。

### 2.3 美学（Aesthetics · 目标美学用明确词汇）

采用 MDA 的八类美学词汇，明确排序与取舍，防止「什么都想要」导致范围蔓延。

**目标美学（按优先级）**

1. **表达（Expression）** — 主导：同一份预算与地块，不同玩家长出形态不同的城市；「我的城市我做主」是核心满足感。
2. **挑战（Challenge）** — 次主导：在土地/预算/通行能力三重约束下做优化，是「可解的谜题」而非「无解的苦役」。
3. **发现（Discovery）** — 支撑：逐步看懂「通勤—覆盖—满意度」的耦合，产生「啊哈，原来如此」的系统理解快感。
4. **消遣（Submission / Pastime）** — 底座：低压、可随时放下、回来还能接上；适配手机碎片时段。

**明确不追求（本作排除项）**

| 排除的美学 | 原因 |
| --- | --- |
| 伙伴（Fellowship） | 单机优先；不引入多人社交/协作/排行作为核心，避免同步与社交系统撑爆 lean 范围（分享类特性仅作可选，见 6.2） |
| 叙事（Narrative） | 不做强剧情战役；市民具象化只用于补「关联感」，不承担故事弧（见 4.1 / OD-3） |
| 感官（Sensation） | 视听是**可读性工具**而非卖点；不追求画面冲击或史诗演出 |
| 幻想（Fantasy） | 现代都市经营是「治理者视角」，不做角色扮演代入、不做架空世界观 |
| 竞争（Competition，Challenge 的对抗性变体） | 无 PvP、无对抗排名；张力来自系统事件而非其他玩家（见 4.2） |

> 一句话：本作是 **Expression + Challenge** 双核、**Discovery + Pastime** 托底的单机经营解谜；排除 Fellowship / Narrative / Fantasy，是范围分层（第 5 节）的直接依据。

## 3. 核心循环（动词优先法）

### 3.1 玩家动词表

先定**玩家在做什么**，再定系统。每个动词必须能映射到一条规则（2.1），否则视为无机制支撑的伪动词。

| 序 | 动词 | 玩家输入 | 系统输出 | 单次耗时（手机） | 对应规则 |
| --- | --- | --- | --- | --- | --- |
| V1 | **读（Read）** | 打开仪表盘 / 看议题卡 | ≤3 个全局指标 + 当前待处理议题 | 5–10 s | R8 |
| V2 | **诊（Diagnose）** | 点开某条议题 | 「为什么降了」的归因链（哪条通勤线/哪片覆盖不足） | 10–20 s | R8, R4 |
| V3 | **划（Zone）** | 在网格上划定/改划分区 | 地块用途变更（即时可见） | 10–20 s | R1, R2 |
| V4 | **拨（Fund）** | 决定本周期建设与维护投入 | 预算扣减、结余更新 | 5–10 s | R3 |
| V5 | **连（Connect）** | 铺设/升级道路 | 通勤图拓扑更新 | 10–20 s | R4 |
| V6 | **推（Advance）** | 结束本日 / 推进 tick | 一次模拟结算 | 1 次点按 | R5, R7 |
| V7 | **察（Observe）** | 看 tick 后的变化 | 指标变化 + 新议题 | 5–15 s | R6, R8 |
| V8 | **调（Adjust）** | 回到 V3/V4/V5 修正 | 新一轮决策 | — | 全部 |
| V9 | **兑（Claim）** | 周期末达成目标 | 解锁新区 / 新政策 / 新的规划目标 | 周期末一次 | R7 |

> 动词优先的结论：本作的核心动词是 **「划 / 拨 / 连」三个决策动词 + 「推」一个节奏动词**；「诊」是防止黑箱感的关键支撑动词，不可省（见 9.1 R4）。**没有「摆楼」「微调单栋」「实时拖动车流」这类微操动词**，这是 P4 的直接结果。

### 3.2 循环图（文字版）

```
                    ┌─────────────────────── 微循环 30~90 s ───────────────────────┐
                    │                                                              │
   ┌──► V1 读 ──► V2 诊 ──► 决策三选一 ──► V6 推 ──► V7 察 ──┐                  │
   │                │         │  V3 划  /  V4 拨  /  V5 连     │                  │
   │                │         └──────────┬───────────────────┘                  │
   │                │                    │ 即时反馈（落位/高亮）                   │
   │                │                    │ tick 后反馈（指标变化/新议题）            │
   │                └────── V8 调 ◄──────┘                                       │
   │                                                                              │
   │   ┌──── 中循环 3~8 min：一个「议题」从出现 → 诊断 → 处置 → 消退/转化 ────┐     │
   │   │  例：东北片区通勤抱怨 → 诊出干道容量不足 → 升级道路 + 补一处服务     │     │
   │   │       → 推 2~3 个周期 → 满意度回升、议题关闭（或转为新议题）        │     │
   │   └───────────────────────────────┬───────────────────────────────────┘     │
   │                                   │ 累积 N 个中循环                         │
   │   ┌──── 宏循环 15~30 min：一个「市政周期」────────────────────────────┐    │
   │   │  R7 预算结算 → P1 满意度判定 → V9 兑（解锁新区/新政策/新目标）      │    │
   │   │  → 土地与预算约束被重新配置 → 回到 V1，开始下一任期                 │    │
   │   └───────────────────────────────────────────────────────────────────┘    │
   └──────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 单次循环时长与心流平衡点

| 层级 | 时长 | 内容 | 心流职责 |
| --- | --- | --- | --- |
| 微循环 | **30–90 s** | 读 → 一个决策 → 推 → 察 | 提供高频、低成本的「动作—反馈」闭环，维持胜任感 |
| 中循环 | **3–8 min** | 一个议题的完整处置 | 提供「问题被我解决了」的成就单元 |
| 宏循环 | **15–30 min** | 一个市政周期结算 + 解锁 | 提供阶段完成感与重新规划的期待 |

**心流平衡点（明确标定）**

- **平衡点 = 「信息可读量」与「决策深度」的交点**：挑战必须来自**约束下的取舍**（P2），而不是来自**信息太多看不过来**。因此认知负载设硬上限：同屏 ≤3 个全局指标、待处理议题 **3±1 条**；超出即触发分层/折叠，而不是加面板。
- **技能—挑战同速上升**：新因子、新分区、新道路等级按「一次只加一个」渐进解锁，每次解锁配一个可诊断的议题作为教学，避免复杂度阶跃。
- **节奏脉冲**：宏循环内安排 1–2 次「危机脉冲」（如预算吃紧 / 通勤拥堵爆发），把挑战曲线从平缓拉起一个峰，随后给「恢复窗口」，形成 `平稳 → 上升 → 峰值 → 回落 →  mastery` 的文字版心流曲线。此为 D2/D3 自然波动，非独立事件系统。
- **可离开的等待窗口**：R5 低频 tick + 默认暂停（**OD-2 A 已拍板，见 8.0**）让「等待」不消耗玩家注意力，这是手机上维持 Pastime 美学、避免焦虑的关键。
- **单次会议目标**：手机上 **5–12 min** 完成一个完整中循环 + 看得见进展；平板/折叠屏可延长到 **20–30 min** 完成一个宏循环。超出即视为节奏设计失败。

## 4. 玩家心理映射

### 4.1 自我决定论（SDT）

| 需求 | 本作如何满足 | 具体落点 | **会被什么摧毁** |
| --- | --- | --- | --- |
| **自主 Autonomy** | 无唯一正解：同一预算与地块允许多种分区/路网组合都能达标 | V3 划 / V4 拨 / V5 连 的自由组合；政策取舍（Should 期） | **伪选择**与**主导策略**——若存在可算出的唯一最优配比，自主感直接归零（见 9.1 R2） |
| **胜任 Competence** | 因果链可读、反馈及时、难度渐进 | V2 诊 的归因链；「即时落位 + tick 后指标」两级反馈；一次只解锁一个因子 | **反馈黑箱**——动作后数秒无可见变化、或满意度变化无法归因（见 9.1 R4） |
| **关联 Relatedness** | 单机城建最薄弱的一环，需**刻意补**：把「市民」从数字变成可感知的对象 | 「市民之声」：投诉信、街访短句、街区画像（**OD-3 A 已拍板，见 8.0**）；把满意度下降表述为具体人的具体抱怨 | 纯仪表盘、无拟人化 → 城市变成一张 Excel，长期留存受损 |

> 关联感的取舍：本作**不通过多人社交**补 Relatedness（2.3 已排除 Fellowship），走「低成本叙事化数据」路线。呈现粒度已由用户按 OD-3 **A** 拍板（聚合数据 + 市民之声），不做具象个体市民。

### 4.2 Bartle 玩家类型覆盖

| 类型 | 覆盖度 | 承载设计 | 备注 |
| --- | --- | --- | --- |
| **Achiever 成就型** | ★★★ 主要受众 | 满意度里程碑、预算结余、周期达标、解锁推进 | 与 P1 单一计分板天然契合 |
| **Explorer 探索型** | ★★ 次要受众 | 系统耦合的隐藏因果（D4 滞后暴露）、政策/分区组合实验、诊断面板的深度 | 由 Discovery 美学支撑 |
| **Socializer 社交型** | ★ 弱覆盖 | 市民之声、城市快照分享（**可选，非承诺**） | 明确不建社交系统；不为此扩张范围 |
| **Killer 杀手型** | ✕ 不覆盖 | 无 PvP、无对抗排名 | 用「对抗性事件」替代：舆论压力、预算危机、通勤爆发等**系统对人**的张力，而非人对人 |

**结论**：本作是 **Achiever / Explorer 向**的单机经营解谜。主动放弃 Killer 与强 Socializer 覆盖，是为了不违背 2.3 的排除项、不撑爆 lean 范围——**不为覆盖而塞系统**，这是范围纪律，不是缺陷。

### 4.3 心流曲线（文字版时序）

| 时段 | 挑战 | 技能 | 状态 | 设计手段 |
| --- | --- | --- | --- | --- |
| 0–3 min 教学 | 低 | 低 | 进入 | 只开放 2 种分区 + 1 类道路 + 2 个指标；首个议题必可解 |
| 3–10 min 稳定上升 | 中 | 中 | 心流 | 逐条解锁因子；「一次加一个」；议题数控制在 2–3 条 |
| 10–20 min 危机脉冲 | **高** | 中高 | 张力峰 | 预算吃紧 / 干道拥堵爆发，给出明确归因线索而非无解死局 |
| 20–30 min 恢复 + 结算 | 中 | 高 | 掌控感 | 处置见效 → 周期结算 → V9 解锁 → 新一轮规划期待 |

- 焦虑区（挑战 >> 技能）由「软着陆 + 可诊断 + 可回退」封堵（见 9.1 R5）。
- 无聊区（技能 >> 挑战）由「新区解锁带来的新约束」与「议题情境化、无唯一解」封堵（见 9.1 R2）。

### 5.2 MVP 垂直切片边界（本轮最重要的可落地约束）

**切片定义**：一条从头到尾**完整可玩、可判定成败**的闭环，而不是一堆并列的系统雏形。

```
空地（有限网格）
  → 划 3 类分区，铺 1 类道路连成通勤网
  → 拨一个周期的预算（收入 / 建设 / 维护 / 结余）
  → 推若干 tick，观察满意度 4 因子的变化与议题出现
  → 用「诊」定位一次问题并「调」修正
  → 市政周期结算：满意度达标 / 未达标
  → 达标则 V9 解锁下一块地，进入第二轮；未达标可回退重试
```

**切片内必须有（缺一不可）**
1. R1 有限网格 + R2 分区 + R4 通勤图 + R5 tick + R6 满意度 4 因子 + R3 预算 + R7 周期结算 —— 七条规则全部贯通，不允许「先做半套」。
2. V1→V9 全动词可达，尤其 **V2 诊**不可省。
3. 一次完整的「失败—诊断—修正—见效」体验，用于验证心流与因果可读性。
4. 手机竖屏单手可完成；本地存档可断点续玩。

**切片外明确没有**
- 无公共交通、无政策卡、无地价、无多道路等级、无危机事件、无跨设备、无折叠屏双栏、无季节昼夜、无成就、无分享。
- 不追求地图规模、建筑数量或美术完成度；**切片验收看「闭环通不通」，不看「内容多不多」**。

**验收标准（可玩性判定，交给严守真执行）**
- AC1：新玩家在无外部说明下，10 分钟内完成首个市政周期并理解「分区—通勤—满意度」的基本因果。
- AC2：任一满意度变化都能通过诊断面板追溯到至少一条具体原因。
- AC3：存在至少 2 种明显不同、且都能达标的分区/路网方案（验证无主导策略、验证 Expression）。
- AC4：单次会议 5–12 min 内可完成一个完整中循环并看到可见进展。

## 6. 差异化定位与鸿蒙平台特性

### 6.1 与经典城市建造的取舍

| 维度 | 经典 PC 城建 | 经典手游城建 | **HC-01 的取舍** |
| --- | --- | --- | --- |
| 核心计分 | 人口 / 地价 / 多指标并行 | 收集 / 升级 / 数值成长 | **取**：满意度单一计分板（P1）；**舍**：多指标并列与数值成长线 |
| 时间模型 | 高频连续实时模拟 | 现实时间挂机 + 等待计时 | **取**：低频 tick + 默认暂停（**OD-2 A 已拍板**）；**舍**：高频连续、现实时间挂机 |
| 交通深度 | 逐车个体仿真、微观路径 | 常被简化为装饰 | **取**：抽象但因果可读的通勤图（D1/D2）；**舍**：逐车粒子、也**舍**纯装饰化 |
| 经济模型 | 复杂财政/产业链 | 软货币 + 加速道具 | **取**：预算机会成本与维护费剪刀差（P2/D3）；**舍**：付费加速、无成本扩张 |
| 交互密度 | 多面板、快捷键、可长时间沉浸 | 弹窗与列表密集 | **取**：分层 UI、≤3 指标、30 秒决策（P4）；**舍**：嵌套菜单与多面板并行 |
| 单次时长 | 60 min+ | 碎片但被等待计时打断 | **取**：5–12 min 一个完整中循环、随放随接 |
| 目标 | 造得宏大 / 摊大饼 | 收集满图鉴 | **取**：把有限土地经营到最优（Expression + Challenge） |

**一句话差异化**：不是「更小的 Cities」，而是**「把城建当一份要月月结平的预算案来解」**——少一点造景欲，多一点治理感；把 PC 城建的规模快感换成手机上的**可读懂、可复盘、可放下**。

> 铁律：以下任一项**不得进入 Must**，且须经程基岩（架构）确认可实现性后才可排期。本节只做设计侧价值评估，不代表技术可行结论。

| # | 特性 | 玩法 / 体验价值 | 依赖与风险 | 建议档位 |
| --- | --- | --- | --- | --- |
| H1 | **秒启 / 原子化服务卡片**：桌面卡片直接显示城市状态（≤3 指标 + 待处理议题） | 把「读」这个动词前移到桌面，强化随放随接；不进游戏也能知道「该回城了」 | 需卡片刷新机制与轻量数据通道；风险是变成变相挂机催促，违背 Pastime 美学 | **Could**；若做，卡片**只读不可操作** |
| H2 | **折叠屏控显分离**：上半屏地图、下半屏仪表盘/决策面板 | 与 P4「可读优先」天然契合：两栏让「地图」与「数据」不再抢同一屏，是四项里设计收益最高的一项 | 需 UI 框架支持双栏与展开/折叠态切换；需定义折叠态回退到竖屏分层的规则 | **Should**（优先级最高的平台特性） |

## 7. 视觉锚点（给美术总监 · 8 条）

> 以下 8 条为**明确、可执行、可验收**的锚点，供 `design/art/art-bible.md` 展开。凡与 P4（可读优先）冲突的美术提案，以本节为准。
> **v1.0 对齐说明（2026-11-05）**：按主理人裁定清单，**仅锚点 1 的视角措辞做了折中回改**（采纳美术圣经 §2.1 的 2:1 dimetric / 约 26.57°，C-2 已拍板 A），允许 L0/L1/L2 三个固定缩放档位；**其余 7 条锚点的视觉要求逐字保持不变**（锚点 7 仅同步了引用路径字符串）。本节**与美术圣经 v0.2 已对齐**。

1. **视角**：固定 **2:1 dimetric 等距**（约 26.57°）或 **30°–45° 范围内的单一锁定角度**，**以美术圣经 §2.1 定稿为准**；**不做自由旋转、不做连续自由缩放，允许 L0 / L1 / L2 三个固定档位切换**（档位定义见美术圣经 §2.2）。网格线在「规划态」显性显示、在「观赏态」淡出，两套态要有明确视觉切换。
2. **色调倾向**：**低饱和清冷底色 + 克制的功能色编码**。基底为混凝土白 / 灰蓝 / 浅冷灰；分区用高辨识度但低饱和的色相区分（建议：居住=暖琥珀绿、商业=青蓝、产业=橙灰、公共服务=靛紫）。**满意度/告警另用独立语义色，不得占用分区色相**。明确排除赛博霓虹、童话高饱和、末世暖棕。
3. **建筑语言**：**现代主义 / 功能主义几何体块**，模块化楼层、干净的块面，走矢量感或低多边形，**不做写实贴图**。密度 3 档（低/中/高）必须在轮廓高度与体量上一眼可辨；单栋建筑在手机屏上的最小可辨识尺寸以「不小于一个网格单元」为下限。
4. **信息密度（核心）**：**分层显示是硬规范**。默认「观赏态」只呈现城市本体 + ≤3 个全局指标；「决策态」才叠加分区色块、通勤流量线、热力。**任一屏不得出现 1 个以上的数据面板**；编码优先级：图标 > 数字 > 文字。
5. **交通可视化**：通勤流用**线宽 / 亮度**编码流量，**不画逐辆车**；拥堵用语义色脉冲提示；路径要可读但保持抽象，明确反对粒子车流与写实车模。
6. **氛围**：白天、明亮、干净、有秩序感的「**正在被规划的城市**」。环境动效克制（缓移云影、缓慢流线），服务于可读性而非氛围沉浸；不追求史诗感、废墟感、灾难片感。昼夜/季节光照为 Could，非 MVP 强制项。
7. **UI 与安全区 / 可访问性**：竖屏优先，高频操作落在**底部 1/3 拇指热区**；折叠屏与平板需给出「地图区 / 控制区」两栏布局规范及折叠态回退规则；触控目标不小于 44dp 等效尺寸；**分区不得只靠颜色区分，须叠加图案/图标**以覆盖色觉障碍（与 `design/accessibility/accessibility-matrix.md` 对齐）。
8. **状态反馈**：每个玩家动作都要有**两级反馈**——「即时可见」（落位、高亮、扣减动画）+「tick 后可见」（指标变化、议题出现/消退）。严禁出现「点了没反应」的黑箱感，这是 V2 诊 与 R8 的视觉配套。

### 8.1 OD-1 · 核心计分与终局形态（✅ 已拍板 A）

| C | **关卡式任期目标**：每任期有明确达标线，失败重来，通关式推进 |

- **影响面**：经济系统、UI 仪表盘指标数、失败/重来流程、存档结构、成就设计。
- **推荐 A 的理由**：最贴合 P1，避免多目标带来的认知过载与支柱漂移；B 会把游戏推向「记账模拟」并制造不可逆死局风险；C 会削弱 Expression（趋向唯一解）。
- **若选 B/C 的代价**：需同步修订 P1 表述与 2.3 目标美学排序，属支柱级改动，必须回到用户确认。

### 8.2 OD-2 · 时间模型 / tick 节奏（✅ 已拍板 A）

| 选项 | 内容 |
| --- | --- |
| **A（推荐 · 已采纳）** | **主动推进制**：默认暂停，玩家点「结束本日」结算一次 tick，思考时间无限（棋类 / 解谜感） |
| B | **低频自动制**：tick 自动流动（建议 1 游戏日 ≈ 3 s 实时），可暂停 / ×1 ×2 ×4 |
| C | **现实时间制**：离线也推进，回来面对变化（牵挂感，但需后台权限与离线结算） |

- **影响面**：模拟循环架构、存档/断点、后台权限、跨设备流转（H3）、离线逻辑、单次会议时长。
- **推荐 A 的理由**：最贴合「秒启 + 5–12 min + 随放随接」的移动定位，且规避后台运行与时间同步的架构复杂度；B 保留为 Should 期的「自动播放」可选项，不构成推翻。
- **边缘情况提醒（无论选哪项都需架构处理）**：暂停中操作的排队、tick 结算过程中重复点按、切后台/折屏切换时的状态冻结、跨设备续玩时的时间基准一致性。
- **若选 C 的代价**：与 Pastime 美学冲突，易引发等待焦虑，且需重新评估 H1/H3。

### 8.3 OD-3 · 市民的呈现粒度（✅ 已拍板 A）

| 选项 | 内容 |
| --- | --- |
| **A（推荐 · 已采纳）** | **聚合数据 + 少量「市民之声」文本**：投诉信、街访短句、街区画像，低成本高代入 |
| B | **具象个体市民**：有名字、有通勤路线、可跟随查看，代入强但模拟与文案成本高 |
| C | **纯数据仪表盘**，不做任何拟人化 |

- **影响面**：叙事/文案工作量、UI 面板数量、数据表结构、长期留存策略。
- **推荐 A 的理由**：在 lean 范围内补上 4.1 的 Relatedness 短板，且不拖累低频 tick 架构；B 会把模拟粒度拉到个体级，与 2.1 R5 / 5.1 Won't 冲突；C 则让城市退化为 Excel。

### 8.4 OD-4 · 地图与扩张模型（✅ 已拍板 A）

| B | **无尽生成地图**：长期可玩，但平衡与性能无上限 |
| C | **多个独立城市场景 / 关卡**（不同地形与目标），内容量线性增长 |

- **影响面**：地图数据结构、进度系统、关卡设计量、性能预算、MVP 验收口径。
- **推荐 A 的理由**：MVP 垂直切片必须有明确边界；且「土地有限」是 P2 机会成本成立的前提，B 会直接抽掉这条支柱，C 会把 lean 范围变成内容生产线。

### 9.2 需与程基岩（架构）对齐的事项（经主理人中转，**已确认闭环 · 2026-11-05**）

> **状态（2026-11-05 · 已确认闭环）**：OD-1 ~ OD-4 已全部按 A 拍板；下列五项**已确认闭环（架构 §11.6 / §3.2.1，经主理人中转，2026-11-05）**，不再悬空。
> **追溯约定**：下列 5 条编号项的文字为**设计侧提出诉求时的原文，逐字未改**，仅作「当时提了什么」的留痕；其中的「仍需架构确认」等措辞属**提出时点的状态描述**，**当前状态以每条之后的「架构结论」与本节末尾的闭环声明为准**。
> **路径约定**：下文落点中的 `architecture.md` 指 `docs/architecture/architecture.md`；`ADR-00x` 指 `docs/architecture/adr/` 下对应文件；`systems-index` 指 `design/gdd/systems-index.md`。

1. **OD-2 时间模型（已按 A 拍板）**对模拟循环、存档与后台权限的约束仍需架构确认（A 方案架构最轻的结论仅为设计侧评估，非技术定论）。
   - **架构结论（转述）**：**可行且架构最轻**。渲染帧循环 + 事件驱动一次性确定性 tick 事务；存档 = 自包含快照；**不需要后台保活 / 精确闹钟 / 离线结算 / 时间同步 / 时钟防篡改**；暂停态命令排队、结算中重复点按由 InputGate 拒、切后台只冻结 + 存一次。
   - **落点**：`architecture.md` §3.1 / §3.3 / §11.6 第 1 项、ADR-002、ADR-003。
2. **有限网格规模上限**（建议 24×24 ~ 32×32）与低频 tick 下的性能预算、通勤图求解开销。
   - **架构结论（转述）**：**钉 `32×32 = 1024` 格为 MVP 硬上限、`16×16` 起步按里程碑解锁**；分区块合并 `B ≤ 64`，单次结算估算亚毫秒 ~ 数十毫秒（**建议基线，须 S-12 真机校准，不得当承诺值**）；瓶颈在 DrawCall / 合批 / 内存而非求解。
   - **落点**：§10.2 / §11.2 / systems-index A-3 / ADR-002。
3. **折叠屏 / 平板双栏布局**（H2，Should）所需 UI 框架能力与折叠态回退规则。
   - **架构结论（转述）**：**有条件可行，仅 Should、不进 Must**。UI 框架 6 项能力、形态回退状态机（接口异常统一回退 folded 单栏，「功能不降级，只降信息密度增益」）、降级 4 条（启发式宽高比判形态 / 固定上下分栏 + 手动留白 24dp / 安全容器内缩 / 纯 UI 重排）；全部系统能力经 PlatformAdapter 隔离；**须真机验证后方可排期**。
   - **落点**：§8 / §11.3 / A-9 / ADR-001。
4. **跨设备流转**（H3，Could）的存档同步与状态一致性前提——OD-2 / OD-4 已拍板，仍须架构确认后方可评估。
   - **架构结论（转述）**：**技术上可实现但收益 / 复杂度比不成立，明确不进排期**。OD-2 / OD-4 拍 A 后状态是静止离散短快照，「拍板 A 让迁移变容易，却同时让迁移变没必要」；且引入并发冲突消解、依赖预览版分布式 API、与 5–12 min 短会话冲突。仅预留 `ISaveStorage` 能力位，不实现同步。
   - **落点**：§11.4 / ADR-003。
5. **「诊断面板」的数据可得性**：V2 诊 需要保留 tick 间的指标差分与归因链，架构需确认状态快照策略。
   - **架构结论（转述）**：**可行**。逐 tick 自包含 `TickSnapshot`（`t-1` / `t` 双帧 + `Δ_t` + 归因链 + 命令溯源 + `schemaVersion` / `configHash` / `engineVersion` / seed）；结算时记录归因、查询只读不重算；Keyframe + Delta 保留、冷归档 ≥3 周期覆盖 D4 滞后暴露；**回退只恢复 Keyframe 并丢弃其后 Delta，无需逆运算**。
   - **落点**：§4.1~§4.3 / §11.6 第 5 项 / ADR-002 / ADR-003。

> **本节结论系转述架构侧，设计侧不另下技术结论；详细可行性论证以 `docs/architecture/architecture.md` §11.6 与 `design/gdd/systems-index.md` §7 为准。**
