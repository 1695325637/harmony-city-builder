## 1. 系统目标与支柱映射

### 1.1 系统目标

把 01 的 `ΔS` 归因链、03 的拥堵明细、04 的预算告警、02 的分区错配，组装成玩家**看得懂、点得开、能据此行动**的「议题卡」与「诊断面板」，承载 **V2 诊**、**R8 状态可读**、**AC2 可追溯**，并用 **OD-3 A 的「市民之声」**补上单机城建的关联感（SDT Relatedness）。

### 1.2 支柱映射

| 支柱 | 本系统如何服务 | **本系统不得命中否决列的红线** |
| --- | --- | --- |
| **P4 拇指宽的决读优先** | 活跃议题硬上限 **3±1 条（2~4）**；一条卡 = 一个问题 + 一条归因 + 一个建议动词；诊断面板一次只展开一个 | ❌ 不得同屏堆叠 >4 条议题；❌ 不得一屏出现 2 个以上数据面板；❌ 不得要求跨屏记忆数据（R3） |
| **P1 满意度是唯一计分板** | 所有议题最终都指向「它怎么影响 `S`」 | ❌ 不得设立与 `S` 无关的独立目标 / 成就 / 完成度 |
| **P3 城市是流动系统** | 归因必须落到具体通勤线 / 片区 / 账目，不做「模糊提示」 | ❌ 不得用无来源的通用提示替代归因链 |
| **OD-3 A 关联感** | 「市民之声」把聚合数据表述为具体人的具体抱怨 | ❌ 不得做具象个体市民（有名字 / 可跟随 / 个体模拟）；❌ 不得用多人社交补关联 |

### 1.3 拍板约束核对（OD 全 A）

- **OD-1 A**：议题不判负；未达标可回退重试，议题状态随快照回滚 ✅。
- **OD-2 A**：议题在 tick 结算后生成 / 消退；暂停态只做即时 UI 反馈 ✅。
- **OD-3 A**：**聚合数据 + 市民之声文本**，不做个体市民 ✅（本系统的核心交付之一）。
- **OD-4 A**：议题范围限定在固定有限地图内 ✅。

## 2. 玩家动词与输入输出

| 动词 | 玩家输入 | 系统输出 | 反馈级别 | 对应规则 |
| --- | --- | --- | --- | --- |
| **V1 读（Read）** | 看 HUD 议题列表 | 2~4 条议题卡（标题 + 状态图标 + 一句摘要） | 即时（<100ms） | R8 |
| **V2 诊（Diagnose）** | 点开一条议题 | 归因链：主因因子、涉及的通勤线 / 片区 / 账目、建议动词（V3/V4/V5） | 即时（<100ms） | R8, R4 |
| **V7 察（Observe）** | 看 tick 后变化 | 议题出现 / 消退 / 转化 + 市民之声文本 | tick 后 | R6, R8 |
| **V8 调（Adjust）** | 按建议动词去划 / 拨 / 连 | 下一次 tick 后议题状态变化 | tick 后 | 全部 |

> **V2 诊 不可省**（概念 5.2）：没有归因链的议题只是通知，不构成诊断，AC2 无法通过。

## 3. 规则 / 数据结构

### 3.1 议题卡数据结构

```
Issue = {
  id             : int,
  type           : enum {COMMUTE, SERVICE, ENVIRONMENT, FISCAL, BUDGET, ZONING, TUTORIAL},
  title          : string,                 // 短句，≤ 12 汉字为宜
  summary        : string,                 // 一句聚合数据表述
  cause_ref      : {                       // 归因链（必须非空，E1 除外）
     primary_factor : enum {f_c, f_s, f_e, f_f},
     dS_i           : float,                // 该因子贡献 [分/tick]（来自 01）
     detail         : string                // 哪条通勤线 / 哪片覆盖不足 / 哪笔投入
  },
  suggested_verb : enum {V3 划, V4 拨, V5 连},
  citizen_voice  : string | null,          // 市民之声（OD-3 A），可为 null
  priority       : float,                  // 排序分（见 4.3）
  state          : enum {NEW, ACTIVE, RESOLVING, CLOSED, CONVERTED},
  born_tick      : int,
  quiet_ticks    : int                     // 连续未满足触发条件的 tick 数
}
```

### 3.2 议题类型与来源

| 类型 | 来源系统 | 触发信号（占位阈值见 4.2） | 建议动词 |
| --- | --- | --- | --- |
| `COMMUTE` 通勤 | 01 + 03 | `f_c` 下降 / `T_c` 超阈 / 路段 `q/cap` 饱和 / `unreachable` | V5 连、V3 划 |
| `SERVICE` 服务覆盖 | 01 + 03 | `f_s` 下降 / `t_g` 超阈 | V5 连、V3 划（补商业） |
| `ENVIRONMENT` 环境负荷 | 01 + 02 | `f_e` 下降 / `E` 超阈 | V3 划（产业外移 / 降密度） |
| `FISCAL` 财政投入 | 01 + 04 | `f_f` 下降 / `I_f` 不足 | V4 拨 |
| `BUDGET` 预算告警 | 04 | `B_t < 0` / `C_m` 阶梯上升 / `I_t` 下滑 | V4 拨、V3 划（降密度 / 拆冗余） |
| `ZONING` 分区错配 | 02 | `ρ` 越界 / 全图单一分区 | V3 划 |
| `TUTORIAL` 教学 | 05 自身 | 首 tick / 新因子解锁 | 对应新动词 |

> **`TUTORIAL` 不来自模拟异常**，用于概念 3.3「一次只解锁一个因子，每次配一个可诊断议题作为教学」，不引入独立教学系统。

### 3.3 生命周期

```
触发条件成立 → NEW（生成，含市民之声抽样）
  → ACTIVE（参与优先级排序，进入 2~4 条列表）
  → 玩家按建议动词处置后条件仍弱：RESOLVING
  → 连续 k 个 tick 条件不再满足 → CLOSED（消退）
  → 或主因变化 → CONVERTED（转为另一类型的新卡，不叠加）
```

- **`n_issue` 硬上限 2~4 条**（共享数据字典）。超过 4 条时按 4.3 的 `priority` 保留前 4 条，其余**同类合并 + 列表折叠**，不堆叠、不新增面板（R3 / P4）。
- 议题**不判负**、不设失败态；`CLOSED` 是自然消退，不是「任务失败」。

### 3.4 市民之声（OD-3 A 的文案形态与触发规则）

| 形态 | 说明 | 示例语气（非定稿文案） |
| --- | --- | --- |
| 投诉信 | 针对具体问题的第一人称短句 | 「早高峰又堵在东路口了，上班迟了两回。」 |
| 街访短句 | 无指向的氛围性一句 | 「这半年，楼下总算有地方买菜了。」 |
| 街区画像 | 一片区的聚合状态描述 | 「东北片区：通勤偏长，服务点偏少。」 |

**触发规则（占位）**

| 规则 | 内容 |
| --- | --- |
| 绑定 | 每条 `citizen_voice` 必须绑定一条 `Issue` 及其 `cause_ref`，**不得出现与聚合数据矛盾的文本** |
| 抽样 | 每 tick **最多生成 1 条新文本**（防刷屏 / 防认知过载）；`NEW` 议题按 `priority` 优先抽样 |
| 正负双向 | 不仅抱怨：`S` 显著回升 / 议题 `CLOSED` 时也可生成正向短句，强化胜任感 |
| 更新 | 文本随议题 `CLOSED` 一同归档；同一议题不重复生成多条文本 |
| 不做 | ❌ 具象个体市民（无名字 / 不可跟随 / 不参与模拟）；❌ 剧情弧 / 对话树；❌ 个体市民数据面板 |

> 文案量产与本地化容器规格以美术圣经 §7.3 与 `design/ux/ux-spec.md` 为准；本 GDD 只定义**形态、触发与数量上限**。

## 4. 核心算法 / 公式骨架（触发、排序、消退）

> **全部阈值为占位符**，只锁定结构、量纲与取值范围原则。

| 量 | 骨架公式 | 变量与单位 | 取值范围原则 |
| --- | --- | --- | --- |
| 触发 | `trigger_i = ( |ΔS_i| ≥ θ_i ) ∨ ( f_i < f_floor ) ∨ ( q/cap ≥ θ_cong ) ∨ ( B_t < 0 ) ∨ ( ρ ∉ [ρ_lo, ρ_hi] ) ∨ ( unreachable )` | `ΔS_i [分/tick]`；`θ_i [分/tick]`；`f_i / f_floor` 无量纲；`q/cap` 无量纲；`B_t [CU]`；`ρ` 无量纲 | 所有 `θ > 0` 且有限；`f_floor ∈ [0.2,0.5]`（与 01 的 4.2 **同值**）；`ρ_lo < 1 < ρ_hi`；阈值不得密集到每 tick 刷屏 |
| 排序分 | `priority = a1 × |ΔS_i| + a2 × severity + a3 × min(quiet_ticks, a_cap)` | `|ΔS_i| [分/tick]`；`severity` 无量纲（预算告警 / 不可达加权）；`quiet_ticks [tick]`；系数 `a1,a2,a3` 使各项量纲归一 | `a1,a2,a3 ≥ 0`；`BUDGET` 与 `unreachable` 给固定加权；教学期 `TUTORIAL` 置顶；**确定性排序**（同输入同结果） |
| 消退 | `if (¬trigger_i 连续 k 个 tick) → CLOSED` | `k [tick]` | `k ≥ 1`，建议 `k ∈ [2,3]`；与 D4「滞后暴露」一致，不允许刚处置就立刻消失 |
| 转化 | `if (primary_factor 变化) → CONVERTED`（生成新卡，旧卡关闭） | — | 转化**不增加** `n_issue` 总数 |
| 数量钳制 | `n_issue = clamp( Σ ACTIVE , 0, 4 )`；`>4` 时合并同类 + 折叠 | `n_issue [条]` | **硬上限 4**；教学期下限可放宽到 1；正常期 2~4（3±1） |

**取值范围通则**：所有阈值 `> 0` 且有限；排序不依赖随机数（可回放，01 的 AC-F4）；`n_issue` 任何时刻不超过 4。

## 6. 边界与 Won't

### 6.1 边缘情况（≥3 类，逐类给出处理原则）

| # | 边缘情况 | 处理原则 |
| --- | --- | --- |
| E1 | **归因链为空**（`ΔS = 0`、首 tick 无 `t−1` 快照） | 不生成归因型议题；首 tick 只生成 `TUTORIAL` 卡，`cause_ref` 可为空并明确标注「教学」；绝不编造归因 |
| E2 | **活跃议题数超 4 条** | 按 `priority` 保留前 4，其余**同类合并 + 折叠**（不堆叠、不新增面板）；被合并项不丢失，可在折叠区查看 |
| E3 | **多个因子同时恶化** | 每条卡绑定 `|ΔS_i|` 最大的**单一主因**，其余因子作为 `detail` 补充；不生成「一条卡四个主因」的模糊卡 |
| E4 | **议题在玩家处置前自行消退**（D4 滞后 / 系统自恢复） | 走 `k` 个 tick 的静默观察窗，**不立即关闭**；若期间条件复现则回到 `ACTIVE`，避免「刚要处理就消失」的挫败 |
| E5 | **回退重试后议题状态不一致** | 议题状态随周期初快照一并回滚（A-6）；不得出现「`S` 回退但议题仍显示已解决」 |
| E6 | **市民之声与聚合数据矛盾** | 文本必须与 `cause_ref.primary_factor` 方向一致；生成前做方向校验，不一致则不生成该条文本（宁缺毋滥） |
| E7 | **同一问题被多个系统同时上报**（如拥堵 + 覆盖同时恶化） | 按 `primary_factor` 去重；同类合并为一条卡，`detail` 列出多个来源 |
| E8 | **玩家长时间不处置议题** | 议题保持 `ACTIVE` 并参与排序，不惩罚、不判负、不弹窗催促（OD-1 A / Pastime 美学） |

### 6.2 Won't（明确不做）

- ❌ 不做具象个体市民、市民跟随、个体级数据面板（OD-3 A）。
- ❌ 不做强剧情 / 对话树 / 故事弧（概念 2.3 排除 Narrative）。
- ❌ 不做独立「危机事件系统」；`BUDGET` / `COMMUTE` 告警来自 03 / 04 的自然波动（概念 5.2 切片外）。
- ❌ 不做成就、任务链、分享、社交（切片外 / 2.3 排除 Fellowship）。
- ❌ 议题**不写回任何模拟状态**（只读汇聚，避免隐藏反馈环与不可归因）。
- ❌ 不定义 UI 布局、状态存储、快照实现（UX 与架构职责）。
